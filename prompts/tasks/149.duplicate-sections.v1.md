## 調査結果・未解決

- 初回同期と監視イベントは別々に同じパスのリクエストを追加できるが、単一 IndexWorker は逐次処理し同じパス・ハッシュの既存セクションを再追加しない。
- 複数 writer の不存在確認と追加は原子的ではない。#150 の共有モックによる重複再現と整合するが、報告された事例の原因は未確定。
- maintenance_repair は正常な重複を修復しない。force 指定も同一ハッシュのセクションを再生成しない。現在 JSON-RPC は rebuildIndex を拒否する。
- 安全な検出・修復と writer 切り替え時の再発防止には設計上の判断が必要。関連 Issue との切り分けを conductor に報告する。
- Issue に調査方針と確認結果を記録した。コード変更、テスト、実データの変更は行っていない。

## 追加調査: 修復とキュー

- 一時 LanceDB で親子 2 組から一組を ID 指定削除し、再接続・同じ削除の再実行を確認。delete の直前・正常復帰直後に子プロセスを強制終了する試験でも、再接続後の再実行を確認した。delete 実行中の中断や障害は未検証。
- heartbeat や現行 stop は修復期間の排他を保証しないため、実データを変更する修復機能は実装していない。検出には親子グラフと曖昧な候補の取り扱いが必要。
- 同一ミリ秒の pending 2 行について、一方を processing とした後、厳密な時刻比較の skip 条件で他方が pending に残ることを一時 LanceDB で確認。余分な処理を生じるがセクション重複の実証ではない。
- 詳細、運用上の保全・隔離の選択肢、未検証事項を Issue に記録した。

## 先行実装の方針

オペレータは読み取り専用の重複候補検出とキューの余分な処理の削減を先行する方針を選択。原因確定、安全な自動修復、完全な再発防止はこの先行作業では未達。固定 snapshot、走査不完全の明示、同着・更新・処理中追加・失敗再開を検証し、実データは変更しない。

## 先行実装・検証

- `diagnose_duplicates` は固定した sections の版を読み、同一パス・ハッシュの完全に一致する親子の木を重複候補として表示する。50,000 行・64 MiB で不完全とし、判定不能・省略も表示。部分重複の網羅や現在時点を保証せず、修復しない。
- IndexWorker は取得済み ID に限り、選択した要求の索引処理成功後に同一ハッシュまたは古い要求を skip。失敗時は他の要求を残す。新規追加や同着・異なるハッシュは対象を誤って拡張しない。取得上限・順序と長時間停止 writer の制約は残る。
- 一時 LanceDB の実 DB テスト、snapshot 固定後の並行追加、同着・新旧・処理中追加・失敗／再開、MCP 表示を検証。DBEngine と MCP ハンドラーを使った一時 DB の手動縦断検証も実施。
- 合成 930 文書・9,300 節（各 2,000 bytes）は診断約 0.11 秒、読み取り約 19.5 MB、プロセス最大 RSS 約 253 MB。単一ローカル実験であり性能保証ではない。
- build、lint、対象テスト成功。unit 全体は sandbox 内 FSEvents 開始エラー、sandbox 外で成功。実データは変更していない。
