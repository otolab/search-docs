## 複雑さと懸念

- **複雑度は高い**。filesystem 上の短命な排他登録と DB 内の MVCC / heartbeat が別の資源・別の寿命を持つため、単一の「lock がある / ない」では起動中断の安全性を説明できない。ファイル作成と fsync の間、DB schema 初期化と read-only 診断の間、writer claim と shutdown の間を分けて追う必要がある。
- `gate` / `users` は保守ロックと共有利用の間を調停する。一方、heartbeat は writer の選出であり、全 DB 書込みや DB 初期化完了を保証するものとは限らない。MVCC も操作の隔離・snapshot の性質を確認する対象であり、起動の準備完了やロック所有者の生存を自動で証明するとは仮定しない。
- crash や破損を再現する場合は、必ず新規一時領域か複製 DB を使う。実利用データを変更・削除せず、試験後の状態と cleanup の成否を記録する。
- ローカル単一ホスト・ローカル filesystem の試験から、共有 / network filesystem、multi-host、Windows を含む挙動へ一般化しない。未試験範囲として明示する。
- 部分初期化 DB と既存 DB の恒久破損を判別する根拠がないまま、欠損を無視したり自動作成したりしない。
- 制御試験が現在の lock を通過したことを、現行方式の維持や回収方式の承認として記録しない。

## 現行コードから分かる制御範囲

### 実装上の順序

- MCP / HTTP の通常起動は `gate` の中で共有登録 (`users/<UUID>`) を作り、その後 gate を解放する。サービス起動側は共有登録を保持したまま strict 診断を行う。
- MCP の strict 診断は embedding server / DBEngine の起動前に実行される。診断は read-only DBEngine を `skipInitModel` で接続し、heartbeat と索引・保留 request のパス、文書コピーを確認する。
- strict 診断後にサービス側が DBEngine を writable で接続する。Python worker は provider/model を確認し `embedding_identity` を作成した後、`sections`、`index_requests`、`writer_heartbeat` を順に作り、scalar index を管理する。writer の claim は `connect()` 成功後に始まり、claim 後の `beforeWriter` でも strict 診断を行う。
- `init_tables()` は table 作成失敗を伝播する一方、個々の scalar-index 作成失敗は警告を出して継続する。従って「init_model が成功した」ことは、必ずしも全 scalar index の作成完了を保証しない。
- `gate` は `mkdir` の排他で shared registration と exclusive acquisition の短い判定・更新区間を直列化する。`users` は shared利用の継続中、`exclusive` は破壊的保守中、`incomplete` は保守未完了を示す。いずれもプロセス所有者を記録しない。
- LanceDB の heartbeat は writer 選出に使う。コード上、起動前 strict 診断・`embedding_identity`・全 table の作成や maintenance gate の代替にはならない。heartbeat 自体の読み書きも DB worker の操作であり、全テーブル横断の transaction ではない。
- `markIncomplete()` は親ディレクトリと管理ディレクトリを fsync するが、gate / users / exclusive の作成・削除と identity file の書込みには明示的 fsync がない。SIGKILL 試験はプロセス強制終了後の状態を示すもので、OS crash / 電源断時の耐久性は実証しない。

## 隔離した制御試験の結果

### gate / users / exclusive / incomplete

実行条件: 現行 `maintenance-lock.ts` を一時ディレクトリへ複製し、テスト専用 pause hook を複製側だけに挿入。独立した Node プロセスを SIGKILL で停止した。製品ソースは変更していない。

- `gate` 作成直後に SIGKILL: `gate` が残り、shared の再取得は1秒の待機後に残存 gate として拒否された。試験用領域で gate だけを手動除去すると shared / exclusive のどちらも取得できた。
- user directory 作成後・identity 書込み前に SIGKILL: `gate` と空の user directory が残った。試験用領域で gate を除去後も、shared は identity を読めず拒否され、exclusive は user directory が残っているため拒否された。
- identity 書込み後・gate 解放前に SIGKILL: `gate` と identity 付き登録が残った。gate のみ除去すると同じ identity の shared は追加できたが、別 identity は拒否され、exclusive は既存 user により拒否された。
- 同じ一時領域上で shared と exclusive の別プロセス取得を20回同時に開始: 各回で片方だけ成功し、両方成功または両方失敗はなかった（shared 10回、exclusive 10回）。これは単一ホスト・ローカル filesystem・この実装の短い制御競合の試験に限る。
- exclusive 取得後・`incomplete` 作成前に SIGKILL: exclusive が残り、shared は拒否された。試験用領域で exclusive を手動除去すると shared / `requireComplete` 付き maintenance は取得できた。
- `incomplete` 作成後に SIGKILL: exclusive と incomplete が残った。試験用領域で exclusive を除去しても shared と `requireComplete: true` の maintenance は拒否された。`requireComplete` を指定しない内部 lock API なら排他を再取得し `incomplete` を維持したまま処理後に clear できたが、これは operator-facing な復旧仕様の承認・検証ではない。CLI force-repair と MCP purge は `requireComplete: true` を使う。

### DB 初期化と通常再起動

実行条件: 新規の一時プロジェクトと DB ごとに Python worker の一時複製へ pause hook を挿入し、次の境界で worker を SIGKILL した。Embedding は `/health` 応答だけの loopback fake server で、推論は行っていない。read-only strict 診断の前後で DB tree 内の全ファイル名・内容 hash を比較した。

| SIGKILL 境界 | kill 直後に見えた DB | strict 診断 / hash | MCP 通常再起動 |
|---|---|---|---|
| `embedding_identity` 作成後、必須 table 前 | identity のみ | heartbeat 未作成で拒否 / 不変 | MCP initialize 前に終了 |
| `sections` 作成後 | identity + sections | heartbeat 未作成で拒否 / 不変 | MCP initialize 前に終了 |
| `index_requests` 作成後 | identity + sections + index_requests | heartbeat 未作成で拒否 / 不変 | MCP initialize 前に終了 |
| `writer_heartbeat` 作成後 | identity + 必須3 table、index なし | 診断合格 / 不変 | 起動成功。再初期化で scalar index がそろった |
| index_requests の status scalar index 作成後 | 必須 table + status index のみ | 診断合格 / 不変 | 起動成功。再初期化で残りの scalar index がそろった |

- 先の3ケースでは、strict 診断後の「通常 MCP 起動」は DBEngine の writable `connect()` に到達せず終了した。一方、同じ一時 DB に strict gate を介さず `DBEngine.connect()` を直接行うと、いずれも残りの table と index が作成され、接続に成功した。これは現行初期化処理が部分状態を継続できることを示すが、通常の MCP 経路ではその処理に到達できない。
- 必須 table がそろった後の scalar-index 初期化途中は、strict 診断を通過し、通常 MCP 起動が不足 index を作成して成功した。
- ここでいう SIGKILL は `init_model` の identity/table/index 作成境界に pause した worker を止める試験。`create_table` / `create_scalar_index` の native 処理の途中で kill した試験ではない。
- hash 比較は各 partial-init DB への read-only strict 診断前後では一致した。既存 DB 破損・欠落を修復する処理も診断経路にはなかった。恒久欠落と内容破損も、別の一時 DB で独立に試験した。

### writer 昇格中の shutdown、恒久欠落・破損 DB、起動回帰

- **writer 昇格中の SIGTERM（実測）**: 一時プロジェクトの MCP プロセスを起動し、writer 前の2回目の strict 診断で停止するよう生成済み server bundle の一時複製に pause を入れた。診断用 Python process group が生存中に親へ SIGTERM を送り、診断を再開した。親は診断中には終了せず、再開後に exit 0。Python process group は停止し、`WATCHING` ログなし、heartbeat 0 行だった。fake embedding server は `/health` のみ返し、推論なし。生成物への一時計測は試験後に元へ戻した。
- **5 MCP 起動回帰（実測）**: `parallel-mcp-startup.test.ts` を実行し、新規一時プロジェクトで5プロセスが30秒以内に接続、exclusive を拒否、起動中 SIGKILL 後に再接続する1テストが6.2秒で成功した。workspace root にだけ Vitest があったため package filter 経由では runner を見つけられず、root の Vitest binary を直接呼び出して実施した。
- **DB connect 後・identity 前（実測）**: instrumentation を `Path(db_path).mkdir()` と `lancedb.connect()` の直後に置いて worker を SIGKILL。DB path は存在するが table 0。strict は missing heartbeat で失敗し snapshot 不変、通常 MCP も initialize 前に exit 1。strict を通さず同じ DB に直接 `DBEngine.connect()` すると初期化完了した。
- **恒久欠落 table（実測）**: 完成済み一時DBから `writer_heartbeat` を除いた。strict 診断は `Table 'writer_heartbeat' was not found` で失敗し、前後 snapshot hash は不変。通常 MCP も exit 1、DB hash 不変、users 登録なし。
- **Lance data file 破損（実測）**: 完成済み一時DBの `writer_heartbeat` data file をゼロで上書きした。strict は Lance file の invalid magic error で失敗し、診断・MCP 起動の前後で DB snapshot hash 不変、MCP exit 1、users 登録なし。破損データを隠す自動修復はなかった。
- 上記欠落・破損試験も一時 DB 限定。実利用 DB には触れていない。snapshot はファイル一覧と内容 hash。新規一時環境での再現であり、電源断・OS crash・native table write 中断の試験ではない。

## crash-point matrix

| 停止点 | disk / 登録に残る実測状態 | 通常起動・保守の現行挙動 | 回復上の含意 |
|---|---|---|---|
| `gate` mkdir 直後 | 空の `gate` | 1秒後 gate 使用中として失敗 | process owner が記録されない。全利用停止確認後の手動除去が必要 |
| `users/<uuid>` mkdir 後、identity 前 | gate + 空 user dir | gate 除去後も shared は identity 不在で失敗、exclusive は user count > 0 で失敗 | 作成途中か壊れた登録かをコードだけで識別できない。手動確認が要る |
| identity write 後、gate 解放前 | gate + 有効 user 登録 | gate 除去後も登録は共有利用中として残る | shared 登録の内容だけでは所有 process の生存を証明できない |
| exclusive mkdir 後、`incomplete` 前 | `exclusive` | shared と次の exclusive を拒否 | 変更前でも人手の排他回収が必要になる |
| `incomplete` 作成後、処理 / complete 前 | `exclusive` + `incomplete` | shared は拒否。force-repair / purge (`requireComplete:true`) も拒否 | 明示全再構築 `index recreate` は `requireComplete` を渡さず再試行可能。ただし stale `exclusive` / `users` があれば先に人手確認が必要 |
| DB path 作成・LanceDB connect 後、embedding identity 前 | 一時 DB directory のみ、table 0 | strict は missing heartbeat で拒否し、通常 MCP は接続前に終了。strict hash 不変 | `DBEngine.connect()` を strict なしで直接実行すると初期化成功。通常経路はこの再開に到達しない |
| embedding identity / 必須 table 作成途中 | identity と table の一部 | strict 起動は missing required table で拒否し、書込みなし。strict を迂回した DBEngine 初期化なら残りを作る | 部分初期化と恒久欠損を通常起動が区別できない。迂回を製品動作に採用する判断は未承認 |
| 必須 table 完了後、scalar index 作成途中 | 必須 table、一部 index | strict 合格。起動時の再初期化が不足 index 作成を試みる | index 作成 error は警告継続のため、全 index 完了の保証にはならない |
| strict 診断中（writer 前）に SIGTERM | 診断 subprocess が生存する間は親が終了を待つ | 実測では診断再開後に clean exit、writer heartbeat なし | 試した診断 pause point に限る。SIGKILL / 電源断の子孫停止保証ではない |
| 必須 table の恒久欠落 / data file 破損 | 一時 DB 内に欠損 / invalid file | strict と MCP が fail-closed。read-only 診断前後 hash 不変 | 通常起動は復旧しない。バックアップ復元か、明示的な全再構築候補 |

## MVCC / heartbeat / filesystem 登録の守備範囲

- **実装上の事実**: Python worker は read-only 接続に `read_consistency_interval=5秒` を設定する。heartbeat 読取は別の新規 DB 接続から行う。writer heartbeat は writer election / 活動状態の共有に使われる。strict 起動診断は DBEngine を read-only + `skipInitModel` で開く。`gate/users/exclusive/incomplete` は DB とは別の filesystem 管理領域。
- **公式 API の説明**: LanceDB の `read_consistency_interval` は他 process の table 更新を確認する read 用の設定で、write は常に consistent とされる。LanceDB の version history は table ごとに write commit を記録する。([Python API](https://lancedb.github.io/lancedb/python/python/), [Tables / Versioning](https://docs.lancedb.com/tables/versioning))
- **コードからの推論**: アプリ初期化は embedding identity、3 required table、scalar index を順に別呼出しで作る。DB-wide transaction または全 table の一括 commit/version marker は見当たらない。従って Lance の table MVCC は各 table 内の read/write 世代には関わるが、アプリ全体の複数 table 初期化を一括 rollback したり「初期化完了」を証明したりしない。table create / index build の内部で crash した場合の Lance 回復性は今回未試験。
- **コードからの推論**: heartbeat の存在や更新は writer 選定の材料であり、DB format compatibility、全必須 table の初期化完了、maintenance 状態の修復、filesystem lock owner の生存証明ではない。
- **調査範囲**: `format_version` / `schema_version` / DB version table / migration framework はアプリの db-engine / CLI source に見つからなかった。`embedding_identity` は provider / model / dimension の一致確認であり、schema version や初期化完了 marker ではない。これは検索範囲に基づく結論で、依存ライブラリ内部の format metadata が無いという主張ではない。
- **未実測**: LanceDB の複数 table にまたがる transaction semantics、OS crash / power loss と fsync 永続性、network/shared filesystem、multi-host、Windows は検証していない。SIGKILL はこれらの proxy ではない。

## 回復候補と限界（採用判断ではない）

| 候補 | 利点 | 主な限界・必要な判断 |
|---|---|---|
| 現行の fail-closed + 明示 `index recreate` | 新たな永続状態を増やさず、source からの全再構築という既存経路で `incomplete` を再試行できる。確認・隔離・保存先検査とマーカーを使う | 全 index を作り直す破壊操作で、元文書が再取得可能でなければ復旧できない。stale gate/exclusive/users の自動回収はしない。table 単位 repair / purge は incomplete を拒否 |
| 自動 stale lock 回収 | gate などの放置で起動不能になるケースを減らす | 現行 dir に PID / host / start token がなく所有者を判定できない。PID/lease だけでは PID reuse、複数 host、停止中 process、fencing の問題が残る。heartbeat は別資源の writer election で代替根拠にならない |
| DB 内 init-ready marker | partial-init と ready DB を区別する足がかりになる | marker 自体の作成・更新順序と durability が要る。同じ DB に置くと途中作成 / 破損時の意味を定義する必要がある。外部 marker は DB と二資源になる crash window と identity binding が生じる |
| DB format version + migration | 将来 schema の識別と移行経路を明示できる | 現状 framework がない。migration の順序、再実行安全性、途中失敗、旧版互換・backup・downgrade を別途決める必要があり、version 値だけで ready を保証しない |

### multi-host 前提と試験限界

`strictMaintenanceLock()` は標準の兄弟配置、symlink でない directory、local path の `realpath`、親と index/documents/management の `st_dev` 一致を検査する。実 lock は共有 path に対する `mkdir` と directory marker であり、`gate/users/exclusive` に owner host / PID / start time / fencing token はない。これらの確認は同一ホスト内の配置検査であり、複数 host 間の原子性・可視性・partition 時の排他保証を証明しない。

本環境には独立した第二 host と、製品運用対象として指定された shared/network filesystem がないため、multi-host の同時取得・network partition・NFS/SMB のキャッシュ反映・host reboot・lease fencing は実施できない。従って前回の20回 raceも今回の試験も multi-host の証拠ではない。明示的復旧の安全条件としては「到達できる全 host、旧 version、process descendants、直接 DB access の停止確認」と「全利用者が同じ management directory を見ている確認」が必要だが、接続不能 host の不在はこの環境から検証できない。

**operator decision（inq-1）**: 対象は単一 host とし、複数 host での利用は非対応と明記する。この決定で multi-host 対応の検討は今回の対象外になるが、filesystem の種類や同一 host 内の複数 process の調停条件まで決まったわけではない。

単一 host の範囲でも、協調する全 process が同じ実体の DB path と management path を参照し、管理領域上の directory `mkdir` が競合時に原子的に一方だけ成功すること、作成・削除が他 process から適切な時点で見えることが必要になる。`st_dev` の一致と `realpath` は配置の一部を検査するだけで、これらの意味や障害後の永続性を証明しない。特に別 host からも同じ shared/network filesystem に接続できる構成は、製品としては非対応である。shared/network filesystem を単一 host だけが使う構成の対応可否も、今回のローカル一時 filesystem 試験からは判断できず、運用対象の filesystem を指定した追加検証が必要になる。

### conductor への選択肢・帰結・推奨

1. **保守と利用 client の契約**: (a) `users` を全協調 client lifetime に使う、(b) reader 等の登録を減らす、(c) OS / coordinator lock に置換する。 (a) は破壊的保守中に reader も止める現在の保証を保つ一方 stale directory を手動確認する。 (b) は利用 client が見えなくなるため、読者と destructive maintenance の重なりを許せる根拠が必要。(c) は全参加者の移行と各 filesystem / platform の試験が必要。**推奨**: どの利用者を maintenance から守る必要があるか決めるまで `users` を弱めない。これは現在の機構自体を採用する決定ではなく、保護対象を未定義のまま削らないための順序提案。
2. **partial DB の recovery target**: (a) current source が取れる時の全 recreate、(b) 同じ世代の backup による index + documents restore、(c) strict を迂回した writable init の継続、(d) explicit maintenance recovery を新設。今回 (a) は partial DB + incomplete から source がある場合に成功し、source 無しでは hash を保って拒否。(b) はDB診断を回復したが incomplete は別途残った。(c) は現在のDBEngineが不足 table を作れるだけで、破損と partial を区別しない。(d) は仕様設計が必要。**推奨**: automatic continuation を採らず (a)/(b) の適用条件と管理 marker の正式な回復手順を決める。backup restore を用意する場合、index と documents の同世代性、backup integrity、format compatibility、stale management markers の扱いを定義する。
3. **format / writer start**: (a) marker なしで strict fail-closed、(b) new-empty-only initialization、(c) format-versioned resumable migration + ready marker、(d) explicit maintenance からだけ復旧。 (a) は既存状態を増やさないが自動継続しない。(b) は初回識別と startup race が要る。(c) は version互換・再実行/rollback・durability が要る。(d) は手動介入と新 command 仕様が要る。**推奨**: strict を迂回して欠損 table を作る案は採用しない。自動復旧を必須とするかを決め、それが必要な場合に readiness/version の commit point と旧 DB 移行契約を先に設計する。
4. **host の対応範囲（inq-1 決定済み）**: operator は (a) 単一 host を対象とし、複数 host は非対応と明記する案を選択した。これは multi-host support を今回の要件に含めない決定である。shared/network filesystem を単一 host から使う構成まで対応と認めたわけではない。**未決定の前提**: 同一 host 内の全協調 process が共通の DB / management path を使うこと、filesystem 上の `mkdir` 原子性と directory 更新の可視性、必要な永続性、および別 host からの同じ領域へのアクセスを運用上排除できること。今回確認したのは macOS の単一 host / local temporary filesystem に限られ、NFS/SMB 等の保証はない。
5. **停止未確認の扱い**: 今回の実サービス fault 試験では parent MCP は exit 0 でも diagnostic child process group が残り、registration を残したことで exclusive が拒否され writer も開始しなかった。lock 実装の採否とは別に、停止未確認時に同等の排他を保つ必要性は実測された。**推奨**: 代替する場合も、残存 child がいる間に destructive maintenance を許さない同等条件を設計・試験する。

- `cleanup-failure.mjs` は child 起動後に意図的な失敗を起こす。最終確認では child の `SIGKILL` 終了と close 後の temp root 削除を assertion で確認した。

開発中に一度 cleanup helper の import 漏れで harness が temp root を保持した。記録された2つの process group は `kill(pid, 0)` が `ESRCH` であることを確認し、該当する使い捨て root だけを削除した。import と registry の newline 処理を直した後の全実行では cleanup が通っている。

## inq-4: 必須 table 完備後の scalar index（2026-11-27）

### operator 選択と適用範囲

operator は「exclude：必須テーブルが揃っている場合の scalar index は部分 DB の自動補完禁止と区別し、現行の起動時 index 作成を維持する方向で検討する」を選択した。これは設計比較の対象を定める判断であり、製品仕様の実装開始、現行の failure handling の承認、#180 の SIGKILL 条件の縮小・受け入れ条件変更ではない。

したがって比較上は次を区別する。

- `sections` / `index_requests` / `writer_heartbeat` の必須 table が欠けた DB は、通常 startup が自動補完する対象から除外する。#180 の要求範囲もそのまま維持する。
- 必須 table がすべてある DB の scalar index 欠落は部分 DB の table repair と区別し、現行 `init_tables()` の起動時作成を維持する方向で検討する。
- 個別 index 作成失敗後に writer startup を許すか、起動を失敗させるかは未承認。以下の実測は現行実装の挙動を示すだけで、どちらかの仕様承認ではない。

### コード上の事実

- writable `init_model()` は embedding identity の照合後に `init_tables()` を実行し、TypeScript の `DBEngine.connect()` は `initModel()` が success を返してから接続を `ready` にする。
- `init_tables()` は必須3 table を先に作成する。table の作成例外は外へ伝播する。
- scalar index は `index_requests` の status (BITMAP)、document_path (BTREE)、document_hash (BTREE) と `sections` の document_path (BTREE)、is_dirty (BITMAP)、document_hash (BTREE) の計6件。各 `create_scalar_index()` と `wait_for_index(... timeout=60s)` の組を例外 catch し、警告を出して次へ進む。table 単位の index 管理も外側で警告 catch される。
- strict 起動診断は必須 table の読取り、heartbeat、path/request と保存文書の整合を確認するが scalar index の存在は列挙・必須条件化していない。
- したがって現行挙動では、一つの scalar index 作成が失敗しても `init_model()` / `DBEngine.connect()` が継続し、strict 診断を通過して writer に進む余地がある。scalar index 不足による query 性能低下の程度は本調査では測っていない。LanceDB の公式資料も scalar index を filter の高速化用途として説明している（[Python API](https://lancedb.github.io/lancedb/python/python/)）。

### 隔離試験の実測

追加した [`scalar-index-failure.py`](183-recovery-control/scalar-index-failure.py) は実 LanceDB 0.30.2 と現行 `SearchDocsWorker.init_tables()` を使い、各5,000行、vector dimension 256 の一時 DB で `index_requests.status` の `create_scalar_index()` 呼出しにだけ `RuntimeError` を注入した。native API 内部の途中失敗や process crash は注入していない。

- 例外後も `document_path` と `document_hash` の index が作られ、`sections` の3 index も作られた。status index だけが欠けた状態で `init_tables()` が戻った。
- この状態で TypeScript `diagnoseStrictConfig()` は成功した。read-only 診断前後の sections / index_requests / writer_heartbeat の全論理行 hash は一致した。
- status pending と sections dirty の filter 結果は、index 欠落中・retry 後で一致した。次の `init_tables()` で status index が作成され、その後の warm check でも論理行 hash は不変だった。
- macOS の local temporary filesystem、Python 3.11.13 / Node.js 24.16.0 / LanceDB 0.30.2 のこの1回では、例外を含む初回 pass 24.5ms、欠けた1 index の retry 7.1ms、全 index ありの warm check 2.7ms。小さい合成 DB の単一観測であり、統計的 benchmark、実データ規模の性能保証、故障時の上限値として扱わない。

**推論・限界**: 現行の catch-and-continue は scalar index の部分欠落を通常 startup 可能な状態として扱い、次の writable startup が再試行する。実測では選んだ logical rows / filter の結果が保たれたが、native index build 中の SIGKILL、同時 writer、全 query 経路、破損した index metadata、巨大 DB の build time を検証していない。index build が同期接続の途中にあるため、大規模 DB では startup の待ち時間になる。各 index wait はコード上最大60秒を渡しており、逐次に複数個失敗する場合の最悪所要時間は測定していない。

試験資材の再現手順は [`183-recovery-control/README.md`](183-recovery-control/README.md) に追記した。`scalar-index-failure.py` は直接 worker method を呼ぶ制御試験であり、HTTP / MCP の writer readiness が失敗時にどう見えるかを end-to-end で試してはいない。厳密な acceptance test には、新規 fixture と本番同等サイズ DB に対する startup time、query parity、index create/wait の error/timeout、再起動 retry、writer ready 判定が必要になる。どこまでを CI 制約にするかは仕様・性能要件として未決定。

### HTTP shutdown の故障経路（実サービス）

追加した [`http-shutdown-unconfirmed.mjs`](183-recovery-control/http-shutdown-unconfirmed.mjs) は disposable project で実 HTTP server / DBEngine / CLI stop を起動し、コピーした `strict-diagnostic.js` だけに writer 前診断 pause を挿入した。製品 source は変更していない。Node.js 24.16.0 / macOS / local temporary filesystem / fake embedding endpoint で実測した。

- writer 前の診断 worker process group が pause して生きている状態で、実 CLI `stopServer()` が `/shutdown` を呼んだ。
- route の応答は、実 CLI process 内の `fetch` を記録して直接採取した。HTTP 200 / `application/json; charset=utf-8` / body `{"status":"shutting down"}`。server parent は exit 0。CLI は `/health` の応答がなくなったことを根拠に「Server stopped successfully」と報告し、PID file を削除した。
- writer claim は固定値でなく、read-only DBEngine で `writer_heartbeat` row を直接読み、`writerId` / host / PID が server parent と一致し、`state=claiming` であることを確認した。server log に `Claim won, transitioning to watching` があり、`→ WATCHING` はなかった。つまり claim は成立していたが、この停止窓では `WATCHING` へ移っていない。以前の `writerStarted: false` は固定値であり、claim の有無を示す証拠ではなかったため削除した。
- HTTP shutdown 直後の読み取りでは診断 worker process group がまだ存在し、`ps` 上も PPID が 1 に変わった `uv` process を確認した。一方、同じ group を 25ms 間隔で観測すると、この再実行では親終了から **27ms** 後に消失した。原因や実際の DB 書込みは測っていないため、「停止後も worker が継続して生存する」とは言えない。shutdown code 自体が停止を待って確認したわけでもなく、消失までの短い orphan 窓が観測された、という限定された結果である。
- shutdown 後も heartbeat row は `claiming` のまま残り、`users` registration は1件、別 process の `acquireExclusive()` は「データを使用中のプロセスがあります」で拒否された。これは writer activity や open file handle を示すものではない。
- これは HTTP route が診断 worker を停止確認したという試験ではない。route は `WatcherProcess.stop()` を呼ばず、`JsonRpcServer.stop()` → `SearchDocsServer.stop()` → main `DBEngine.disconnect()` の経路のみを進み、成功後に `process.exit(0)` する。diagnostic child が pause していても route の直接停止対象外だった。
- signal 共通 cleanup (`server.ts`) には watcher 停止、失敗集約、`diagnosticStopUnconfirmed` 時の registration 維持があるが、HTTP route はその cleanup coordinator を呼ばない。今回 `users` が残ったのはその marker を通じて保持したからではなく、直接 `process.exit(0)` で正常 cleanup を飛ばしたため。CLI は HTTP成功応答後に health disappearance だけで成功扱いし、child / shared registration の結果を検査しなかった。
- この HTTP fixture は専用 temporary project、実 server / CLI、fake embedding endpoint、同 project の LanceDB を使う。pause worker は fixture の server が起動した strict diagnostic subprocess であり、server process 終了後の orphan 窓も含めて自分の harness が観測する。cleanup はこの harness が起動した child / process group とその temporary root だけを対象にする。今回の直接 HTTP 観測は server route を変更せず、CLI process 内の fetch response を複製して status/body を採取した。

この実測は inq-2 の「停止未確認なら shutdown failure、共有登録を保持する」方向に対し、CLI/server が success を返した後に registration が残り、診断 group が短時間 orphan として観測されたことを示す。停止確認が成立したかを製品が判定した結果ではない。停止未確認時に外部から診断 worker を再試行停止すること、実際の SIGTERM/EPERM fault、HTTP から in-process WatcherProcess を停止する挙動、Node child cleanup の race は未試験。production behavior を修正する実装は未承認なので行っていない。

**必要な設計判断・推奨**:

1. HTTP `/shutdown` を signal handler と同じ cleanup coordinator に接続し、watcher・DBEngine・embedding child・registration の順序と stop error を集約するか。現行の成功応答を維持すると、観測したように parent が成功 exit しても child が残り得る。**推奨**: inq-2 の停止確認 failure 条件を HTTP にも一貫して適用し、未確認なら stop success を返さず shared registration を保持する。
2. CLI の完了判定を `/health` disappearance / PID disappearance とするか、shutdown結果・server exit status・registration/child停止を含む通知 protocol にするか。現行は error exit でも health が落ちれば成功扱いとなる。**推奨**: server が明示的に確認した shutdown 結果を判定根拠にする。具体的な HTTP status/response、CLI retry deadline と signal fallback は未承認。
3. stop が未確認で親も停止しない場合の再試行対象・回数・signal順序、また親だけ終了した場合の stale users / PID の保全と手動回復は別仕様として決める。PID file を CLI が成功時に消した後は、現行の force-stop fallback の手掛かりも失われるため、結果不明と確認済み成功を同じ扱いにしない。

### Recovery 安全条件と未決定事項（inq-3 を踏まえた再確認）

基本経路はオペレータ選択どおり「元文書から明示的に全再構築」か「正常 backup の復元」とする。部分 DB の自動補完は行わない。inq-4 は必須 table が揃った DB の scalar index 作成だけを別に扱い、必須 table 欠落 / 破損の扱いを変えない。

| 経路 | 安全に実行する前提候補 | 現在の限界 / 未決定 |
|---|---|---|
| 元文書から `index recreate` | 同一 host の search-docs service、MCP/HTTP、診断 subprocess、background task とその descendants をすべて停止確認。coordinator `users` が空、stale gate/exclusive の所有 process がないことを手で確認。現行 source glob/exclude と ignore rules を確認し、索引を全消去する明示確認を行う。元文書に権威ある現行内容があり、再embedding に必要な provider/model が使える。 | destructive。source から消えた文書や以前の index にしかない内容は戻らない。current lock owner proof はなく、directory stale の自動回収は未承認。1つの snapshot による原子切替ではない。 |
| 正常 backup から restore | 全 process 停止と backup 時点の整合した snapshot を確認。index と対応 documents を同一時点から組で復元し、backup hash/manifest、embedding identity、schema/application version compatibility、作成者・取得時点を確認。元を上書きする前に現状 DB / documents と maintenance metadata を別保管。復元後は required tables/readability/source keys を strict diagnose。 | 「正常 backup」の判定基準・取得時の writer quiescence・世代識別・integrity manifest は未定義。過去試験は既知 good temp copy の byte-wise 復元のみで、production backup protocol は検証していない。 |
| `incomplete` を解消 | recovery action 完了後に `incomplete` を消す条件を別途定義する。候補は full recreate が全件完了し strict diagnose 成功後、または検査済み backup の index+documents+identity+format を復元し read-only diagnose 成功後。 | いずれも解除条件として未決定。DB と filesystem marker を一つの atomic transaction にできる根拠はない。marker 先行削除は失敗再開時に不完全 DB を通常起動へ開放する。marker 永久保持は復旧後も service を止める。自動解除・新 recovery command は承認されていない。 |
| `format/migration` と writer readiness | 追加しない案は strict fail-closed を維持。導入する場合は version ownership、migration step の再実行性、compatibility matrix、backup/downgrade、failure resume、reader/writer order、last-step ready marker を定義する。writer claim は必要 table/schema/identity/format/maintenance status の検証後に限定する候補。 | app-level format version / migration framework は source に見当たらない。marker なしでも、欠損 table と legacy/破損 DB の区別はつかない。format version 値だけでは他 tables の transaction 完了を証明しない。scalar index 欠落を writer readiness の条件に含めるかは別途未決定（inq-4 は起動時作成維持「方向」の選択）。 |

**事実 / 推論の線引き**: control harness は、source 不在時の full recreate を no-op 拒否、source 復帰後の全再構築を成功、既知の good backup で index+documents の DB strict diagnosis が復帰する一方 `incomplete` が残って shared registration を拒否することを観測済み。これは隔離 fixture の条件を満たした時だけの実測である。実運用 source の完全性、backup の作成時点・読み取り可能性、異なるバージョン間の restore、marker を安全に解除する手順は未検証。backup を戻して strict diagnose が通るだけでは maintenance recovery 完了とは言えない。

### 現行コードで確認した事実

- Unix の `stopProcessTree()` は子の PID を process-group ID として使い、まず `kill(-pid, 0)` で存在を確認する。`ESRCH` のみ不在と扱い、`EPERM` などは不明として throw する。確認後は SIGTERM を一度送り、最大 5 秒間 process group の消失を待つ。SIGTERM の送信が `EPERM` ならその場で throw し、signal 再試行も SIGKILL escalation も行わない。Windows 分岐は直接 child の exit を待つだけだが、strict storage admission は Windows を拒否する。
- `DBEngine.disconnect()` は worker group の停止確認後にのみその group を追跡集合から外す。失敗時は共有登録を解放する後続処理に到達せず、rejected `disconnectPromise` を消去するため低レベル API を再度呼ぶ余地はある。
- strict 診断は専用 `DBEngine` を作り、read-only 接続を閉じる際の停止確認失敗を `UnconfirmedProcessStopError` にする。この diagnostic engine は `diagnoseStrictConfig()` のローカル変数で、失敗後に service lifecycle から停止を再試行できる handle として返されない。
- MCP の `createService()` は diagnostic stop failure を記録し、release closure を no-op にして共有登録を保持する。一方 `ServiceLifecycle.shutdown()` は stop 前に instances を `null` にし、shutdown Promise を memoize する。signal handler も初回 signal 後の再入力を無視する。従って現状は「登録を保持する」一方、同じ lifecycle からの明示再試行はできない。
- `packages/server/src/bin/server.ts` の signal cleanup は diagnostic stop failure だけで `errors` に項目を追加せず、登録 release を skip する。ほかに cleanup error がなければ shutdown を成功扱いし得る。既存 MCP service harness で実測した親の exit code は **0** で、診断 process group は残存、`users` は1件保持、exclusive は拒否、`WATCHING` なし、index section 0件だった。選択された「停止未確認なら失敗」の通知条件はこの実測では満たされていない。
- HTTP の `/shutdown` は cleanup 完了前に 200 `shutting down` を返し、その後 `JsonRpcServer.stop()` を呼んで成功時に exit 0 する。これは server entrypoint の共通 cleanup 経路を通らず、`JsonRpcServer.stop()` は `SearchDocsServer.stop()` と HTTP listener close を行う。停止 fault 時にこの route がどう振る舞うかは実サービス試験していない。CLI の `server stop` は response が成功扱いなら health endpoint が応答しなくなるまで待ち、timeout / request error では PID を使う force-stop fallback に進む。API response、親 process の終了、diagnostic child group の終了は現状別々に扱われている。

### shutdown 通知・停止確認・再試行の候補

| 論点 | 候補と安全上の帰結 |
|---|---|
| **停止確認の成功条件** | (a) leader child の exit のみ、(b) Unix process group の不存在まで確認、(c) platform ごとに child / descendant の保証を分ける。診断 worker の子孫が DB を使い続ける窓を塞ぐには (b) が強い。`EPERM`、PID 情報なし、期限切れは成功扱いせず不明として登録を保持する。ただし process-group ID の再利用と権限境界は単一 host でも残る。 |
| **通知と親の終了** | MCP の SIGINT / SIGTERM はプロトコル応答を返す要求ではないため、(a) stderr に失敗を報告し非ゼロ exit、(b) process を停止済み扱いせず、機能を止めたまま状態表示・再試行を可能にする、の候補がある。(a) は host に失敗が伝わる一方、disk 上に stale `users` が残り、以降は明示確認が要る。(b) は同じ process から再試行できるが、service lifecycle と readiness の degraded state が必要。どちらも登録を自動解放しない。 |
| **HTTP `/shutdown`** | (a) cleanup と停止確認後にのみ成功 response を返し、失敗時は明示的な非成功 response と登録保持を返す同期契約、(b) 202 + operation ID と結果照会 endpoint、(c) route を廃止し signal / CLI のプロセス監視だけに統一、が候補。現行の先行 200 は停止完了を示すものとして使えない。CLI が単なる health endpoint の不在を全 process 停止と同一視しないこと、失敗 response を受けたときに PID force-stop へ進むかを別に決める必要がある。 |
| **停止要求の再試行** | (a) 現行どおり SIGTERM 一度 + 5 秒確認後に失敗、(b) bounded SIGTERM retry、(c) grace period 後に診断専用 worker へ SIGKILL escalation、(d) 無期限待機。(b) は一時的な競合に効く可能性があるが EPERM を解消せず待ち時間を増やす。(c) は read-only diagnostic では候補になり得る一方、共通 `stopProcessTree()` への適用は書込 worker を巻き込むため別仕様が必要。(d) は誤成功を避けるが supervisor timeout により外から SIGKILL され得る。現時点の推奨は、成功条件を緩めず、有界 wait 後も不明なら失敗・登録保持とし、SIGKILL escalation は明示承認まで加えない。retry 回数・間隔は未決定。 |
| **lifecycle 内での再試行** | (a) 非ゼロ終了後、次回起動の前に stale registration を管理者が確認する、(b) 親を degraded のまま残して同一 child handle への retry 操作を提供する、(c) shutdown 内で bounded retry する。現行は再試行可能な engine handle を保持せず、lifecycle Promise も memoize する。新 API・状態機械なしで同じ lifecycle の retry が可能とは推定できない。 |

**安全上の推奨**は、診断 worker が止まったと証明できない場合に成功 response / exit 0 を返さず、共有登録を保持すること。MCP signal 経路は stderr と非ゼロ exit を組み合わせるのが最小の通知候補だが、現在の service harness は exit 0 を実測しており、故障通知経路を別途設計する必要がある。HTTP route は先に成功 response を返さない契約が必要になる。ただし同期・非同期のどちらを採るか、親を終了させるか、retry endpoint を用意するかは未決定。

### `incomplete` と復旧の境界

strict 診断 worker は read-only であり、その停止失敗は destructive maintenance が途中まで進んだ証拠ではない。従って diagnostic stop failure だけを理由に新しく `incomplete` を作るべきとは推論できない。一方、すでに `incomplete` がある場合は診断停止失敗と別に保持し、通常利用拒否を継続する。

既存の隔離試験では、同世代の `index` + `documents` backup restore 後に DB strict 診断は通るが、`incomplete` は残り shared registration を拒否した。選択肢は (a) source から index 全再構築して処理完了時に既存 API が marker を clear する（source から消えた文書は戻らない）、(b) 世代・format・完全性を検証した backup restore を明示 maintenance action として扱い、exclusive を保持して最終検証後に marker を clear する新仕様、(c) 検証できない場合 marker を維持して fail-closed、である。backup directory ごと管理領域を戻すと stale `users` / lock まで復元し得るため、`index`・`documents` と lock metadata の復元は分けて設計すべきである。いずれも今回は実装・承認していない。

診断 worker 停止未確認後に親が終了すれば、共有登録は process handle を失っても filesystem 上に残る。単一 host では、既存環境の棚卸しを前提に、全 MCP / HTTP process、container、旧版、直接 DB 利用者、診断 process group の停止を管理者が確認する案がある。確認できないときは stale registration を消さない。どの診断情報を提示し、誰がどう解除するか、backup / recreate とどの順序で併用するかは explicit recovery 手順の判断点である。自動削除・自動 marker clear は採用候補にしない。

## operator decision inq-3 と recovery の詳細設計（2026-11-27）

operator は「元文書からの明示的な全再構築と正常 backup の復元を基本経路として設計し、部分 DB の自動補完は行わない」を選択した。この決定は recovery の設計上の基本経路を定める。製品仕様の実装、自動回収、新 lock、永続状態、DB format / migration、backup restore 後の `incomplete` 解除条件を承認するものではない。#180 の SIGKILL 受け入れ条件はそのまま維持し、範囲を狭めない。

inq-1 の single-host 境界も維持する。複数 host からの共有 filesystem 利用は今回の設計対象外で非対応とするが、既存環境が実際にこの前提を満たすかは別途棚卸しする。現状は既存利用者の host 数、container / mount 境界、filesystem、DB・documents・management path の実体、直接 DB 利用、backup の取得・保管・復元実態が確認できていない。リポジトリの利用例や今回のローカル試験から実運用構成を推定しない。

### 回復経路 A: 元文書からの明示的な全再構築

現行 `index recreate --confirm-isolated` を使う候補。部分 DB の残存 table を通常起動で補完せず、全利用停止と対象確認の後、index 全体を作り直す。

現行 CLI の順序はコードで次のとおり確認した。

1. `--confirm-isolated` と対応 platform を要求し、標準配置と index / documents / management path を検査して exclusive を取得する。既存 shared user が残れば取得を拒否する。stale gate / exclusive / users を自動回収しない。
2. exclusive を保持して配置を再確認し、source glob の実体・index 外配置・空でない source set・文書コピー領域との分離を検査する。
3. embedding endpoint とモデル / 次元を一時 DB worker で preflight する。ここまでで失敗すれば、既存 index を削除しない。
4. `incomplete` を作り、既知の index tree 全体を削除して、設定された現在の sources から再構築する。
5. 再構築が成功した場合のみ `complete()` で `incomplete` を消し、exclusive を解放する。処理失敗後は通常利用を止める `incomplete` が残る。診断 worker の停止未確認など lock 保持を要する error は exclusive も残す。

この経路は**破壊的**であり、過去に索引化した全内容を復元する手段ではない。再構築されるのは実行時点で設定から取得できる source のみで、source から削除済みの文書、設定から外れた文書、現在取得できない文書の内容は戻らない。source を再取得できない場合、preflight が通らない場合、未知のファイル・DB 配置を検出した場合は実行せず、backup 経路へ切り替える候補とする。CLI が要求する明示確認は専用領域・全 access 停止・処理中の path 不変更を利用者が確認したことを表すもので、非協調 process の停止を製品が証明するわけではない。

したがって実施条件の候補には、少なくとも以下を含める。

- 現行利用実態を棚卸しし、search-docs の全 instance、container、旧版、診断 process、直接 DB reader / writer の停止方法を確認する。single-host 決定をもって利用実態確認を省かない。
- 設定から解決した index / documents / management の実 path、mount、所有者、対象が search-docs 専用であることを確認する。path・link・mount を処理中に変えない。
- 再取得可能な元文書の所在・対象範囲・除外設定を確認し、実行中に変更されないようにする。対象 source の一覧・hash を復旧前後で照合する案はあるが、利用者向け procedure としては未承認。
- 現在の index / documents と管理領域を操作前に別保存し、復元可能性を確かめる。これは破壊的作業に備える保全案であり、現行 CLI が backup の実在・復元可能性を検証するという意味ではない。
- stale registration が見つかっても、停止根拠がないまま消さない。全利用者と子 process の停止を確認できない場合は止まり、管理者判断に戻す。

### 回復経路 B: known-good backup の復元

元文書がすでに無い場合にも index と文書コピーを戻せる候補。ただし「正常 backup」は名前だけでは成立しない。少なくとも index と documents が同じ復元点の組であり、停止中コピーまたは filesystem snapshot 等で一貫して取得され、全ファイルの完全性を確認でき、対象アプリ / LanceDB / schema / embedding identity と互換である必要がある。取得時刻、対象 project / resolved path、application・DB format 情報、table 構成、embedding provider・model・dimension、hash manifest を backup に記録する案はあるが、現行 backup 形式も保証もなく、必須 metadata は未決定である。互換性や完全性を確認できない backup は復元済みの正常 DB とみなさない。

復元時は全利用停止と exclusive の確認を前提とし、`index` と `documents` の内容を対応する既知 backup から復元する。`.search-docs-maintenance` は DB backup と一緒に置換しない案を推奨する。そこには過去の `users` / `gate` / `exclusive` / `incomplete` が含まれ得て、DB backup と異なる時点の管理状態を復元する危険がある。復元後は backup 内容の hash、strict read-only diagnosis、required table / index / identity、必要な document / section の照合を行う案があるが、検証項目と pass/fail 条件は未決定。

**実測:** disposable project で正常完了済みの index と documents を同世代の offline copy として保存し、別の partial-init DB を再現した後、2 directory を byte-for-byte で復元した。strict diagnosis は通過した。一方、maintenance directory に残した `incomplete` は消えず、shared registration を拒否した。これは backup からの DB 内容復元が可能だった一例であり、破損 backup・version mismatch・live copy・本番 procedure を検証したものではない。現行製品には、この手順のための restore command / completion API はない。

### `incomplete` の解除と通常利用再開

二つの経路は marker の扱いが異なる。

- **全再構築:** 現行 code は再構築成功後に `complete()` を呼ぶ。再現試験では partial-init DB + `incomplete` に対し、source がないと削除前に失敗して DB hash と marker を保持し、source を戻すと全再構築後に marker が消えて strict diagnosis と index read が成功した。これは既存 implementation の観測であり、異なる失敗点や全 production DB の保証ではない。
- **backup restore:** 上記の実測では DB は診断を通っても marker が残り、利用を再開できなかった。marker を消す権限・根拠・操作主体・最終検証条件は未決定である。候補は、(a) 検証可能な backup metadata と post-restore checks を満たした時だけ、保守 lock を維持して明示 complete する、(b) operator / admin の個別判断までは marker を維持して fail-closed、(c) 条件が満たせない場合は source 全再構築に戻る、である。自動 clear は採用・承認されていない。

- `packages/server/src/server/json-rpc-server.ts` の `/shutdown` は cleanup 前に HTTP 200 `{"status":"shutting down"}` を返し、100ms 後に `JsonRpcServer.stop()` を呼ぶ。この停止は `SearchDocsServer.stop()` の DBEngine disconnect と HTTP listener close で、`WatcherProcess.stop()`、server entrypoint の共通 cleanup、local embedding child の停止確認、共有登録の解放を通らない。成功時は `process.exit(0)`、失敗時の明示的 HTTP error response はない。既存の[実測](https://github.com/otolab/search-docs/issues/183#issuecomment-7221191026)では HTTP 200・CLI 成功表示・parent exit 0 の後、diagnostic process group が parent exit 直後に一時残り、`users` は残った。今回この故障を再注入してはいない。
- `packages/client/src/client.ts` の既定 request timeout は30秒。`packages/cli/src/commands/server/stop.ts` は `/shutdown` 成功後に最大5秒 health を確認するが、health の非2xxまたは接続失敗を停止とみなし、PID file を削除して成功を報告する。request error / timeout と health polling timeout は PID fallback に進む。
- `packages/cli/src/utils/process.ts:killProcess()` は PID へ SIGTERM を送り、timeout 後に SIGKILL を送る。最後の process exit wait の boolean を検査せず戻るため、CLI fallback は child 停止確認ではなく parent PID の kill になり得る。shutdown が未確認なら失敗・登録保持という inq-2 の方向と両立するか、明示判断が必要。
- MCP signal は `ServiceLifecycle.shutdown()` から `stopService()` を await する。`WatcherProcess.stop()` の失敗時は共有登録を解放しないが、lifecycle は停止前に instances を null にし shutdown Promise を memoize するため、同じ lifecycle からは retry できない。`stopService()` の `embeddingServer.shutdown()` は fire-and-forget で、local embedding child の停止確認を待たない。停止失敗時の signal handler は stderr と exit 1 を返すが、process 終了後は shared registration が stale directory として残る。
- `stopProcessTree()` の Unix 停止は現状 SIGTERM 一度、最大5秒の process-group 確認であり、retry / SIGKILL escalation はない。一方 `WatcherProcess.stop()` は coordination、sync / index queue、event handler を drain してから DBEngine disconnect するため、shutdown 全体がこの5秒以内に収まる保証はない。

### 詳細設計で選ぶ点

1. **停止確認対象:** inq-2 の diagnostic worker に限定するか、DB worker group と local embedding child も含む全 managed child とするか。OS / process group ごとの保証も必要。
2. **HTTP 完了契約:** 推奨は停止確認後にのみ成功 response を返し、未確認なら非成功 response とする同期契約。status / body は未決定。新規 RPC の受付停止、既存 RPC の drain、shutdown request 自身への応答、listener close の順を設計しないと、競合処理や response 消失が起こり得る。`202 + operation ID` は結果照会を追加できるが、選択された「HTTP shutdown が停止処理を待つ」方向との整合を別途決める必要がある。
3. **timeout / 切断:** child の5秒 wait、watcher drain を含む全体 deadline、HTTP client timeout、CLI の終了待ちを分ける。timeout / 接続断は失敗確定ではなく結果不明で、server 側の停止が継続中か response だけ失われたか現 API では区別できない。新規 request を拒む状態管理や同じ結果の照会が候補。
4. **再試行:** 現行 `/shutdown` に in-flight request をまとめる状態はなく、応答喪失後の再要求で複数の stop 処理が走る可能性がある。request を冪等にして同じ処理の結果を返す、結果照会を設ける、再送しない案がある。HTTP request の retry と SIGTERM の再送は分ける。signal retry / SIGKILL escalation は未承認。
5. **CLI fallback:** 推奨は health 不在だけで成功・PID file 削除とせず、HTTP 停止確認と parent exit を区別すること。結果不明時に自動 PID kill を続けると、child 確認前に parent を止める可能性がある。fallback を廃止するか、利用者の明示 force 操作へ分離するかは既存 `server stop` との互換性を含め要判断。
6. **MCP の失敗後:** stderr + exit 1 は既存 host の終了形を保ちやすいが、shared registration は stale として残り同一 process で retry できない。degraded 状態の process を維持する案は readiness・service handle・retry 経路の追加設計が必要。
7. **共有登録と回復:** child 停止未確認なら registration を release しないのが inq-2 と整合する。parent exit 後の directory は owner handle を持たない。自動回収や手動解除条件は未決定で、今回決めていない。

single-host の対象決定（inq-1 / inq-5）は、現行利用者がその条件内で動いている証拠ではない。既存 CLI / MCP / HTTP client、独自 timeout、supervisor hard-kill deadline、host / container / mount / filesystem の棚卸しが必要。今回の追加作業はコード読解のみで、fault-injection / runtime test と製品変更は行っていない。

詳細な署名付き記録は [Issue #183 の inq-7 コメント](https://github.com/otolab/search-docs/issues/183#issuecomment-7231466355)。#180 CLOSED、#183 OPEN、#188 OPEN を read-only で確認し、いずれの state も変更していない。

### 既存 force / escalation の適用範囲

- **`server stop`** に public `--force` はない。ただし graceful HTTP shutdown が失敗すると、現在は自動で PID fallback を使う。Unix では server PID に SIGTERM、5秒後にその PID へ SIGKILL を送り、子孫 / process group は対象にしない。SIGKILL 後の exit wait 結果も呼出し側で検査せず、PID file を削除する。Windows は `taskkill /T`、timeout 後は `/F /T` で、root PID の終了を確認する。
- **`embedding stop --force`** は実在するが server / diagnostic worker 用ではない。`--port` と PID file / LISTEN owner から対象を選び、owner が特定できなければ `--force` でも拒否する。外部 process を対象にすると警告する。Unix は port owner PID 単体に SIGKILL を送り、process group / descendants 全体は確認しない。Windows は `taskkill /F /T`。process exit・port 解放・health 不通を確認した場合に限り、対応する embedding PID file を削除する。`.search-docs-maintenance/users` には触れず、共有 embedding server なら他プロジェクトを中断し得る。
- `embedding stop` の既定動作も Unix で SIGTERM 後5秒、Windows で `/T` 後timeout時に `/F /T` と、自動 SIGKILL escalation がある。さらに server 内の `EmbeddingServerProcess.stopChildProcess()` は Unix process group へ SIGTERM、5秒後 SIGKILL、Windows では `/T` と `/F /T` を使う。inq-8 をこれらの shutdown 経路にも広げるかは明確化が必要。
- `index rebuild --force` は hash 判定を無視して再索引、`config init --force` は設定上書き、`maintenance force-repair` は table 保守であり、一般的な shutdown force-stop ではない。`killProcessTree()` の自動 group escalation は embedding 起動失敗・中断の cleanup にも使われる。
- server parent を強制終了すると通常 cleanup の共有登録 release closure は走らず、`users/<id>/identity` が残る。登録は PID / host を持たないため directory だけで stale と断定できない。embedding stop は別の embedding PID file を扱うだけで、storage registration を解除しない。

### 保護機構の境界

- LanceDB の MVCC は table 読み取りの snapshot を扱う。プロセス停止、複数 table にまたがる復旧、保守との admission は保証しない。
- heartbeat は writer の claim / lease / failover を調停する。DB 初期化完了、診断 child の消失、保守 owner の不在を証明しない。
- `gate` は共有登録と exclusive 取得の競合を直列化し、`users` は reader も含む共有利用者を登録する。`exclusive` は破壊的保守の排他、`incomplete` は処理未完了時の通常利用拒否を担う。用途が違い、互いの代わりにはならない。
- `users` を writer だけに縮めると、read-only client がいる最中の recreate / restore を止められない。heartbeat を保守 lock の代替にすることもできない。現行機構の維持・縮小・置換のいずれも未承認。
- inq-1 / inq-5 が対象にしたのは非公開 single-host の CLI / MCP ローカル利用と multi-host 非対応である。現利用者がその範囲内かは未調査。同一 host の container / mount を含め、協調 process が同じ実体 path を見て、directory `mkdir` の原子性、状態の可視性、必要な永続性を filesystem が備えることは別の前提であり、今回のローカル fixture はその一般性を検証しない。

### shutdown の提案状態遷移と試験対応

| 状態 | 提案する動作と遷移条件 | 成否・失敗時の扱い | 対応する検証 |
|---|---|---|---|
| `RUNNING` → `STOP_REQUESTED` | 最初の停止要求で一つの shutdown operation を作り、新規 RPC を拒む。重複要求は同じ operation に合流させる。shutdown 要求自身は drain 対象から除く。 | 二重 cleanup を開始しない。 | 重複 HTTP 要求、同時 MCP signal の試験で stop operation が一つであることを確認。 |
| `STOP_REQUESTED` → `DRAINING` | 受付済み RPC の応答を待つ。その後 `WatcherProcess.stop()` で新しい file event / indexing を止め、startup sync、queue、event handler、heartbeat update と writer release を drain する。既存の `stop()` は最後に共有 DBEngine を disconnect するため、HTTP RPC を先に drain してから呼ぶ。 | drain 中の timeout は成功扱いしない。`incomplete` は destructive operation の marker なので shutdown failure だけでは作らない。 | RPC in-flight と index queue を同時に保持し、停止後に新規処理・書き込みがないこと、accepted request の扱い、完了順を観測。 |
| `DRAINING` → `STOPPING_CHILDREN` | strict 診断用の別 DBEngine / Python process group と、Watcher / DBEngine が所有する DB worker group の停止を確認する。診断 child の handle は完了確認まで lifecycle が保持する。ローカル起動した embedding child は indexing drain 後に停止対象とし、外部 provider / 共有 embedding は停止しない。 | `EPERM`、timeout、PID/group 不明、終了確認失敗は停止未確認。現行 `stopProcessTree()` は一度 SIGTERM、最大5秒待機し、SIGKILL へ進まない。 | diagnostic process を pause / fault injection し、各 child group、親、`users`、exclusive 拒否、signal log を観測。DB worker と local / external embedding は別 fixture に分ける。 |
| `STOPPING_CHILDREN` → `STOPPED` | 全 owned child の停止確認、DB disconnect、cleanup 成功の後にだけ共有登録を解放する。HTTP は停止完了後に成功 response を送り listener を閉じる。CLI は response に加えて parent exit を確認してから PID file を消す。MCP も同じ成功条件を使う。 | HTTP success / CLI success / exit 0 は child 確認より先行させない。 | healthy HTTP / CLI / MCP 経路で status/body、child group 消失、writer state、registration release、PID file の順序を取る。 |
| 任意状態 → `FAILED_UNCONFIRMED` | child stop / queue drain / cleanup failure。 | 自動 SIGKILL へ進まず、共有登録を保持し、`incomplete` は変更しない。接続断・client timeout は server operation の cancel とみなさず、呼出元には「結果不明」と返す。CLI は PID fallback signal や PID file 削除をせず、`server restart` は停止成功を確認できない限り起動を中止する。 | child 生存・SIGTERM EPERM / timeout を注入し、非成功結果、registration 維持、exclusive block、SIGKILL 不在、PID file 維持、restart abort を確認。通信切断時は server 側処理が続くかと呼出元の未知状態を別々に記録。 |

この案では shutdown failure 後も shared registration を保つ（inq-2）一方、親 process を degraded のまま維持するか、失敗を返した後 exit 1 するかは未決。推奨は、既存 host の終了契約を崩さず非成功を伝えやすい「応答可能なら HTTP 非成功 / MCP stderr、exit 1、その後も registration は保持」。ただし process 終了後は owner handle のない stale registration になる。代替の degraded 維持は同一 process から再試行できる利点があるが、service lifecycle / readiness / retry endpoint を追加しないと停止要求が永久に終わらない。どちらを採っても、親 PID の終了だけで child stop を推定しない。

timeout は child group の既存5秒 wait、Watcher drain、HTTP client の既定30秒を分けて扱う。client の30秒 timeout を server operation の deadline と読み替えず、切断しても server 処理を cancel しない案を推奨する。Watcher / supervisor の全体 deadline は現利用者と supervisor の終了期限を棚卸ししていないため具体値を置けない。deadline 超過は失敗または結果不明であって signal escalation / registration 解放の理由にはしない。SIGTERM の再送回数、HTTP status/body、同一 operation の結果照会、failed state 後の明示 retry は未決。

inq-8 の no-auto は Issue #183 の service shutdown に適用する案を推奨し、server 内の local embedding child にも自動 SIGKILL escalation を行わない。外部 embedding は所有 process ではないため停止しない。独立した `embedding stop` の既定 escalation / `--force` は別コマンドの契約として分け、今回の回答だけで変更しない案を推奨する。local child への適用範囲は operator の明示確認が必要。

既存 harness は正常 HTTP shutdown と停止中診断の観測を持つが、route 自身に「child 停止未確認」を注入して status/body を観測する試験ではない。以前の実サービス記録では HTTP 200 / CLI 成功 / parent exit 0 の後に diagnostic group が一時残り、約27ms後に消失した一回の観測に限られる。group が残った短時間は確認できたが、DB write 継続や長期生存は示していない。EPERM harness は signal API 差し替えであり、OS の権限・所有者 race を再現しない。

### recovery と既存の手動 lock 除去案内

現行 `docs/user-guide.md` は、全 server / 旧版 / direct DB access / child の停止、実 path・link・mount・backup の確認後に、通常の空 `gate` / `exclusive` を `rmdir` し、`users/<id>/identity` を個別削除して空の registration directory を取り除く手順を記載している。同時に `users` や管理領域の再帰削除を禁じ、`incomplete` は手動削除しないと案内している。別箇所では残存ロックを除いたあと `index recreate --confirm-isolated` を明示実行できるとしている。これは現行 docs の記述であり、本 Issue の operator が stale owner recovery を改めて承認した意味ではない。

問題は registration に PID / host / process group を記録しないため、`identity` は設定照合情報であって所有者証明ではないこと。single-host の利用でも、対象 path を共有する container、他ユーザーの process、旧版、直接 LanceDB access がないことを確認する必要がある。PID file、`ps`、`lsof` / open handle の調査は有用な状況証拠だが、全 OS・権限・別名 mount で不在を証明する共通手段ではない。owner を特定・除外できなければ lock は消さず、管理者へエスカレーションする。

推奨する復旧の境界:

1. 先に実利用環境を棚卸しし、実 DB / documents / management path と同一 host の全 MCP / HTTP / CLI / container / 旧版 / direct access / child の停止を確認する。shared / multi-host filesystem 利用が判明したら single-host 対象外なので、復旧のための lock 削除を進めない。
2. `gate` / `exclusive` / 各 `users` directory は相互に独立した制御情報である。既存 docs の正確な個別削除案を残すなら、全 owner absent の条件と証拠の限界を明示する。再帰削除や不明な entry の削除はしない。手動解除を許さず管理者のみとする代替はより fail-closed だが、復旧を運用者へ委ねる。
3. `incomplete` は lock stale 判定と分け、手動では消さない。元文書からの全再構築は現在の source 一覧が完全・安定し、対象 storage が専用である場合だけの明示的破壊操作。source からなくなった文書は復元できない。成功時の `index recreate` は operation の最後に marker を完了させる経路として扱う。
4. backup 復元は `index` と `documents` が同じ復元点の正常な組で、対象 DB format / embedding identity と互換であることが条件候補。backup が存在することや、その性質は未確認。live path へ restore する際は全 handle を閉じ、maintenance directory を data backup と一緒に巻き戻さない。restore 後の read-only strict / row / document / identity 検証が通っても、現 harness では `incomplete` を解除しない。解除には exclusive 下で検証済み restore を確定させる明示経路とその証跡が必要だが、現在その契約/API はなく、条件を決めるまでは marker を保持して通常起動を拒否する。

過去の隔離 fixture では source recreate が成功し、同一 fixture から作った `index` + `documents` backup restore は strict diagnosis を通ったが `incomplete` が残って shared registration は拒否された。これは test fixture の手操作であり、production backup の一貫性、正常性や recovery completion を立証しない。`incomplete` を消す試験は行っていない。

### writer readiness、scalar index、DB format / migration

現行起動順は `strictMaintenanceLock` → shared registration → read-only `diagnoseStrictConfig` → writable `DBEngine.connect()` → HTTP server / Watcher 起動。Watcher は heartbeat claim / readback 後、`beforeWriter` strict diagnosis を実行し、claim 所有権を再読してから `WATCHING` へ遷移する。strict diagnosis は required table を読むが scalar index の存在を要求しない。`DBEngine.connect()` 内の `worker.init_tables()` は各 table と6 scalar indexを初期化し、個別の `create_scalar_index()` / `wait_for_index()` 失敗を warning にして続行する。`embedding_identity` は provider / model / digest / vector dimension を照合し、DB format/schema version marker ではない。コード上に format version / schema migration framework はない。

**新規の隔離実測:** `scalar-index-failure.py` を実行。temporary LanceDB に `sections` と `index_requests` 各5,000行、256次元 vector を作り、`index_requests.status` の create 時だけ例外を注入。初期化は続き、残り5 index はできた。3 table の logical row count / SHA-256 は障害前後で同じ、pending / dirty filter の ID も同じ。scalar index が欠けても read-only strict diagnosis は成功し、row hash は変化せず、次の `init_tables()` で index が作られた。計測値は first pass 0.0797秒、retry 0.0152秒、warm check 0.0071秒。この小 fixture の一回の時間であり性能ベンチマークではない。TS service startup / writer claim / WATCHING は試しておらず、native index API 内 kill でもない。

## operator decision inq-10: サービス管理 local embedding child にも自動 SIGKILL をしない（2026-11-28）

operator は `apply` を選び、inq-8 の no-auto 方針を**サービスが起動した local embedding child の停止にも適用**すると決めた。inq-9 と合わせた設計方向は、停止確認が取れない child に自動 SIGKILL / Windows `/F` を送らず、失敗を報告し、親 process を終了し、storage の shared registration を保持すること。失敗を表す非ゼロ exit は引き続き推奨案で、数値・通知方式・停止期限は未決。独立 `embedding stop` の通常動作・既存 `--force` の適用、明示 force の使い方、stale registration 回収、新 lock / marker、製品実装はこの回答で承認されていない。

### 現行のサービス管理 embedding child と適用境界

コード読解では、`EmbeddingServerProcess.stopChildProcess()` は Unix で detached process group に SIGTERM を送り5秒待ち、残存時に SIGKILL を送りさらに1秒待つ。Windows は `taskkill /T` の後に終了確認を行い、残存時は `/F /T` に進む。従って inq-10 は既存の強制停止段階を設計上外す方向だが、5秒を採用するか、何回 signal を送るか、最終期限をどうするかは別途未決である。現行 server cleanup は Watcher、server PID file、JSON-RPC server、embedding child の順に停止するため、embedding child の停止確認前に親 PID file を削除してしまう。cleanup error は shared registration を保持するが、起動中 signal の `catch` では cleanup が失敗しても `shutdownRequested ? 0 : 1` により exit 0 になり得る。q9 の「停止未確認なら失敗報告して親終了」と合わせた場合、この終了コード・PID file 順序は未達の設計箇所である。

適用境界にも未整理点がある。同じ `EmbeddingServerProcess` は server だけでなく CLI の `index recreate` / `index purge` からも使われる。inq-10 が明示したのはサービス管理 child であり、共通 helper の変更をこれらの CLI cleanup にも及ぼすかは回答されていない。独立 `embedding stop` は別 command として今回の決定から除外する。実装する場合は caller ごとの policy を明示する案を推奨し、既存共通 helper を一律に変えて scope を広げない。

### 残存登録と同一 identity restart の保証

`MaintenanceLock` の `users/<id>` は identity 文字列だけを保存し、owner PID や child PID を持たない。`acquireExclusive()` は users が1件でもあれば保守を拒む。これは writer だけではなく、共有登録中の read-only 利用者や CLI / MCP の shared operation と排他保守の競合を抑える。users を writer のみに縮めると、read-only process が DB を使っている間に index recreate / purge / restore 等が始まり得るため、MVCC snapshot や heartbeat では代替できない。exclusive は通常利用者を識別する gate と違い、破壊的保守を全 shared user から隔てる役割がある。現行範囲を維持する合理性がある。

一方、q9 の隔離 process 試験で実測したとおり、stale entry があっても**同じ lock identity の `acquireShared()` は許可される**。違う identity は拒否され、exclusive は拒否される。これは既存の同一 storage / files identity による複数 process 利用を維持する一方、停止未確認後に同じ identity の server が再起動できない、という保証はない。identity は embedding provider / model / dimension を含まないため、同じ lock identity でも embedding 設定まで同じとは限らない。heartbeat は writer 選出であり、stale child の終了証明や shared admission fence ではない。`incomplete` も shutdown failure だけでは作成しない。

local embedding の停止未確認にも具体的な再利用経路がある。既定設定では `EmbeddingServerProcess.start()` が `127.0.0.1:24281` の既存 endpoint の readiness を確認し、ready なら自分で起動せず `external` と扱う。その後の `stop()` は自分の ChildProcess handle がないので何もしない。readiness の採用時は `/health` の status と `/ready` の ready を見るが、model / dimension / owner の一致確認はしない。ただし後続の `DBEngine.connect()` は `embedding_identity` の provider / model / digest / dimension と sections dimension を照合し、不一致なら DB 初期化を拒む。したがって「endpoint 再利用時に互換性確認が一切ない」とは言えないが、lock identity に embedding 設定は含まれず、接続先を所有・停止する主体も再起動後には引き継がれない。親終了後に embedding listener が残れば、同一 identity の restart がそれを external として再利用し、以後も停止しない場合がある。これは DB 互換性の拒否で一部を検出できても、child の所有・回収や安全な停止完了を保証しない。

## operator decision inq-11: 停止未確認 child が残り得る場合の同一 identity 起動（2026-11-28）

operator は `allow` を選び、停止未確認の child が残る可能性があっても、同じ lock identity の通常起動を許し、残存状態を診断・案内する方向で設計する。これは自動回収、新 lock / marker、具体的な通知表示、shutdown / recovery 全体の製品実装を承認するものではない。inq-9 / inq-10 の停止失敗時の親終了・共有登録保持と併存する判断であり、保持した registration が同一 identity の起動も止めるとは説明しない。

### 起動許可と既存保護の境界

現行 `strictMaintenanceLock` identity は canonical project root、index / documents path、file selection settings から作られる。embedding provider / model / digest / dimension は含まれない。従って「同一 identity」は保存先と対象文書設定の一致を表し、embedding 設定まで同じという意味ではない。現在の shared admission は同一 identity の users entry が残っていても許可し、異なる identity は拒否する。identity を読めない users entry があれば shared admission 自体を fail-closed にする。

推奨はこの admission を維持すること。既存の複数 MCP 利用を保ちつつ、破壊的 maintenance の排他を残せる。`acquireExclusive()` は reader / MCP / CLI / server を区別せず、users が1件でも残っていれば拒否する。これを writer のみに縮めると read-only process が DB を使っている間に recreate / purge / restore が通り得る。inq-11 はこの保守排他を弱める決定ではない。stale users の自動削除も行わず、owner 不在が確認できないときは exclusive maintenance を通さない。

既存 local-only の設計範囲は inq-1 / inq-5 と同じく単一の非公開 host であり、複数 host から共有 filesystem を使う構成は対象外。試験は macOS 上の `os.tmpdir()` に作ったローカル一時領域を使った。単一 host であっても、gate / registration の directory 作成が原子的であること、関連 path が一貫して同じ filesystem にあることは必要な前提である。現行コードは path の標準配置、symlink、device 番号の一部を確認するが、任意の container mount / filesystem 実装での atomicity や crash durability は実証していない。

### embedding identity と writer heartbeat の限界

DBEngine は接続時に `embedding_identity` の provider / model / digest / dimension と sections の vector dimension を照合し、不一致なら DB 初期化を拒む。現行の `digest` は Ollama の model digest、openai-compatible provider の場合は URL から計算した正規化 endpoint hash で、builtin では空文字となる。いずれも endpoint の process owner / PID / 起動元や、endpoint が申告どおりの model を使い続けることを証明しない。embedding endpoint の health / readiness probe も listener の応答性を見る。従って lock identity の違い検出と embedding identity の整合確認は別の保護であり、どちらも「残った child が終了した」ことを証明しない。

Watcher の stale heartbeat takeover も process 終了検出ではない。現行は heartbeat age が lease を超えると claim を書き、readback と writer 前診断を経て `WATCHING` に進む。heartbeat は overwrite で、owner fencing token や compare-and-swap を備えない。DB / filesystem の遅延や停止した heartbeat と、旧 writer が処理を続けている状態を一般に区別する強い排他証明とは扱えない。inq-11 の再起動許可を「二重 writer が発生しない保証」に拡張してはいけない。

現行 `users/<id>` には lock identity しかなく PID / host / process group / child ownership がない。`acquireShared()` は identity 比較のため既存 entry を列挙するが、active 利用者か停止後の残存かは区別できず、その件数も利用者向け診断としては出力しない。strict diagnosis は DB / source の読み取り専用検査に限られ、この種の状態を報告しない。したがって現在「残存 child を検知・案内できる」とは言えず、inq-11 の operator が選んだ診断方向には実装前の設計差分が残る。

### embedding identity mismatch 起動失敗と registration 解放

`node prompts/tasks/183-recovery-control/embedding-identity-mismatch-cleanup.mjs` を Node.js 24.16.0 / macOS で実行。試験は disposable project / LanceDB を新規作成し、fixture endpoint から `issue183-seed-model` を記録した後、実 MCP `dist/server.js`、実 `DBEngine` worker、実 `MaintenanceLock` を起動した。MCP が起動する local embedding process だけを、`EmbeddingServerProcess` の constructor port を test port に差し替える ESM wrapper と PATH 上の shim で Node HTTP fixture に置換した。identity mismatch 後に child 停止を試みるまで shared registration を保持する readiness gate を用いた。

SIGTERM fault injection は preload から試験専用 process group `40457` に限って EPERM を返すもの。signal-0 や他の DBEngine worker signal は変更せず、その child への SIGKILL も行われていない。観測結果:

- writable connect 先は `issue183-service-model` を返し、DB の `embedding_identity` は `issue183-seed-model`。実 worker log に provider/model/endpoint/dimension mismatch が記録された。
- mismatch cleanup 中に DBEngine worker は disconnect され、MCP log 上 `Python worker exited` は2回確認された（strict read-only diagnosis と writable DBEngine）。`users` は readiness gate 中に1件、その後0件。

- cleanup 時の macOS `kill(-PGID, 0)` は、child group 消失後にも `EPERM` を返すことがあったため、この harness は `ps` の exact PGID と test root command を使って生存状態を確認する。owned PID / command が一致する group だけを停止し、process table から消えた後に一時 root を削除する。停止確認が取れない場合は root を保持する。

### heartbeat lease 失効後の旧 client write

`node prompts/tasks/183-recovery-control/heartbeat-stale-writer-write.mjs` を同じ単一 host の disposable LanceDB で実行。実 `WatcherProcess` の lease timeout を3秒に短縮し、別の実 Node process に DBEngine worker を接続したまま heartbeat を一度 `issue183-old-writer` として記録。自然経過で age が3.03秒となった後、新 Watcher が `claimWriter`、readback、`WATCHING` まで進んだ。その後に限り、旧側から `createIndexRequest` を一回だけ順次実行した。

旧側 DBEngine 呼出しは pending request を返し、新規 read-only DBEngine workerから同じ id/hash/path が読み取れた。旧 parent と両 DBEngine worker process は write 直後に生存、heartbeat owner は新 Watcher のままだった。test harness は native write を重ねず、起動時 `startupSyncWorker` は callback を実行しない stub とした。これは DBEngine API 上の owner fencing がないことを示すが、旧 active Watcher が file indexing / heartbeat を継続する状況、同時 commit や行の重複・欠落・競合、実サービス同一 identity restart を実証するものではない。

今回も製品コード・lock 挙動・受け入れ条件は変更していない。#180 は CLOSED、#183 は OPEN のまま。#180 crash matrix の達成扱いにはせず、未検証の active-writer race と実 embedding runtime の差分を残す。

### q12 を受けた提案状態遷移・判定

製品契約として受け入れるべき方向は次のとおり。signal 再試行や通知方法など、operator が決めていない詳細は実装しない。

1. 起動 attempt は shared registration を保持したまま、開始した子を所有者単位で記録する。失敗したときは依存順を考慮して、開始済みの全 owned child の停止確認を試みる。ある子の確認失敗があっても、別の子に対する安全な停止試行を途中で省かない。
2. 全 child の停止を確認できた場合は cleanup 完了として既存 rollback を続け、registration release の可否は残る cleanup / diagnostic 条件で判定する。
3. 一つでも stop が期限内に確認できない、または確認自体が失敗した場合は failure state とする。inq-10 に従い自動 SIGKILL せず、親は非zeroで終了し shared registration は解放しない。保持 registration は保守の fail-closed を助けるが、同一 identity shared admission、child ownership、data access の安全保証にはならない。
4. child が起動していない失敗、または起動した子を全て止めた失敗は q12 の停止未確認分岐とは区別する。embedding identity mismatch だけで child stop が失敗した事実を成功 cleanup と扱わない。

- **CLI wrapper boundary:** q8 no-auto と合わせ daemon start readiness timeout の親 SIGTERM/SIGKILL fallback をどう止めて failure report するか。foreground start が child nonzero exit を伝える契約、restart が stop failure を「not running」と握りつぶさず扱う条件を設計する。inq-11 の同一 identity restart 許可は保守 exclusion を弱めない。
- **diagnostic/result visibility:** operator は具体通知を選択していない。MCP tool result / stderr / HTTP failure body のどれにどの文言を出すか、MCP refresh 中の graceful exit sequencing は未承認。少なくとも success と誤認させない exit / result code はテスト項目にする。

### q13 に沿う手動経路案（gate に依存しない）

q13 が許した範囲を **共有 `users/<UUID>` 登録の個別除去** に限定する案を推奨する。現行 gate があると lock API も gate 利用の recovery も動かない。運用者が全 launch source を止めた保守時間帯なら、直接 filesystem operation は gate を使わず行えるが、起動抑止が人の運用に依存する。これは gate が手動削除を保護する仕組みではなく、global quiescence を成立させる外部条件である。

1. **利用実態と停止範囲を確認する。** single-host の product 方針だけから実利用を推測しない。対象 storage を使う MCP client / server、HTTP server、CLI foreground / daemon、旧版、direct DB / Python client、local embedding・DB 子・Watcher と、launchd / supervisor / container 等の自動再起動源を実利用者が列挙する。対象 host の全 entrypoint を止め、自動再起動も保守時間中無効にする。親 PID の終了だけ、または PID の存在確認だけでは足りない。process tree と child の停止を確認できない、別 host 利用の有無が不明、または新規起動を止められない場合は何も変更しない。
2. **storage と管理領域を固定する。** 設定から project root を実体解決し、`storage.indexPath` / `documentsPath`、symlink / mount 先、共通 parent、期待される `.search-docs-maintenance` を照合する。停止確認後から完了まで path / mount を差し替えない。場所や物理 storage の一致を確かめられなければ拒否する。
3. **状態を記録し、backup の意味を分ける。** `.search-docs-maintenance` の一覧・file type・内容を回収前の保全記録として退避する場合、これは lock state の証拠で、DB backup ではない。戻すと stale `gate/users/exclusive/incomplete` も戻る。data backup / restore を検討するなら同じ停止時点の index と documents を一組として扱い、両者の互換性・完全性を別途検証する。backup restore alone で `incomplete` を解除しない。
4. **`users` を分類する。** `users` と各 UUID は通常 directory、entry 内の `identity` は regular non-symlink file でなければ拒否する。target identity と byte-for-byte 一致する entry は候補だが UUID に owner はない。identity 欠落 / malformed / mismatched、想定外の中身、symlink は owner を独立に特定できるまで保留し、その1件を理由に blanket delete しない。mismatch / missing の owner と storage が別途確認できず、他 config も同じ物理管理領域を使う可能性を排除できない場合は拒否する。
5. **一致した登録だけを個別に除去する。** 人間確認の保守時間帯を保ったまま、合意した target identity の UUID ごとに identity file を unlink し、その空の UUID directory を rmdir する。`users` や管理領域の recursive delete はしない。前後の一覧を比較し、意図した entry 以外が動いたら中断し、launch source を再開しない。
6. **完了可能性を判定する。** `gate` / `exclusive` が残っていればこれらを変更せず、通常起動・maintenance 操作が拒否される状態として止まる。stale owner を示す情報がなく、q13 はこの marker を除去する許可を含まないためである。`incomplete` も残す。これらのどれかが残った状態の次の操作は、別途承認された復旧仕様なしに進めない。

この案は現在の gate を使えない状態でも、完全停止・新規起動抑止の間に共有登録だけは処理できる。その代わり `gate` / `exclusive` が残るとサービスを再開できず、q13 だけでは回復完了にならない。直接操作中の安全は filesystem lock ではなく人間が維持する outage に依存し、プロセス/launch source inventory が不完全なら成立しない。新 lock・auto reclaim は追加しない。

### 比較する選択肢と operator に必要な判断

| 選択肢 | 現行 `gate` が残るとき | 安全性・限界 |
|---|---|---|
| **A. 外部で全停止・起動禁止した保守時間帯に、一致 identity の users entry のみ直接除去（推奨、inq-13 の狭い適用）** | gate を acquire しないため users の除去操作自体はできる。gate は残り、サービスは再開できない | 新 lock / 自動回収不要。安全性は利用者の完全な実利用 inventory と再起動抑止に依存。gate/exclusive 回収にはならない |
| B. 既存 gate を取る明示 recovery operation | 取得不能で fail closed。stale gate を修復しない | 通常時の競合直列化はできるが、reviewer が指摘した gate 残存時の経路を解決しない。新 API/CLI の製品実装も未承認 |
| C. operator 確認の上で stale gate / exclusive も手動除去 | gate API を使わず除去できるが、どちらも owner / active maintenance を示す情報がない | q13 の対象範囲を拡張する決定が必要。新しい再開許可となり誤判定の帰結も大きい。現時点では行わない |
| D. 新 lock / owner lease で stale 判定・自動回収 | 別の marker で排他を得る案は可能でも既存状態との整合が必要 | 明示的に未承認。候補の実装・試験はしない |

operator に必要な判断は次の2点に絞って返す。

1. `manual` は **A の external offline procedure** を意味するか。対象は一致 identity の `users/<UUID>` だけとし、identity 欠落 / mismatch / unknown content は default refuse とする案を推奨する。必要な host / application / process-tree / launch source の全停止と再起動抑止を利用者が確認できなければ実行しない。
2. stale `gate` / `exclusive` について、q13 の範囲外として保持して停止するか、同じ人間確認の下で手動除去する範囲拡張を別途認めるか。推奨は **保持して停止**。前者のままではこれらが残る環境で回収完了できず、管理者へ引き渡す必要がある。`incomplete` は引き続き変更対象外。

利用実態 inventory と OS 別の停止確認基準は既存 environment の利用者が確認すべき事項で、inq-1/5 の「単一ローカル host」前提だけでは済まない。今回それらを実地確認していない。`docs/user-guide.md` には、管理領域退避と data backup の違い、現在は状態別手順が不足していることを追記したが、上記未決状態の marker clear 手順は掲載しない。

## operator decision inq-15: 正常経路と不安定期間を分ける（2026-11-28）

operator は、これまでの個別登録回収案について「複雑すぎる。正常動作と例外動作は分けるべき。完全に動くならよいが限界がある」と指摘した。inq-15 では「『不安定な時間』を許容するべきです。それをロックで保証します。正常かどうか分かれば使う側が対応できます。そのための情報を増やすべきです」と回答した。

これは管理領域全体の初期化・消去、特定形式の新 lock、既存 lock の維持、自動回収、backup restore 完了、製品仕様の実装許可を意味しない。前の個別 `users/<UUID>` 削除案は既定にしない。ここでは「通常利用」と「移行・初期化・保守が確定するまでの例外期間」を別の状態として扱い、例外時の可視性と全体の復旧経路を簡素にできるか再検討する。

### 現行実装で区別できる状態と限界

| 現在の機構 | コード上の役割 / 寿命 | それだけでは示せないこと |
|---|---|---|
| `gate` | `mkdir` で shared / exclusive の登録変更を短く直列化する。既存 gate は約1秒待って拒否 | owner、実行中か crash residue か、DB が正常か。gate は短期調停用で durable phase record ではない |
| `users/<UUID>` | shared 利用者を登録し、graceful release まで残す。crash 後も残り得る | process / child の生存、writer か reader か。strict identity は root / storage / file 設定を表すが PID / host / owner はない |
| `exclusive` | active maintenance 中は shared と別の exclusive を拒否する | 誰が何をしているか、DB を変更する前か後か、放置されたものか |
| `incomplete` | `markIncomplete()` 後に通常 shared を拒否し、`complete()` まで残す。directory sync を行う | 現在の作業 phase、破損箇所、restore 成功、他の標準 startup initialization の完了 |
| MVCC / Lance table version | テーブルごとの更新と snapshot/version history を持つ。upstream の形式仕様も table version の manifest / MVCC を説明する | search-docs の複数 table をまたぐ全体 commit、application readiness、lock owner / process fencing。project code に DB 全体の transaction は見つからない |
| `writer_heartbeat` | 120秒 lease を使う watcher writer の選出・状態共有 | DB 初期化完了、maintenance admission、停止した process の証明。lease は失効後の旧 DB client write を fence しない |

MVCC の範囲については [Lance table format の一次仕様](https://github.com/lance-format/lance/blob/main/docs/src/format/table/index.md)を参照した。これは table format の説明であり、pin 済み `lancedb==0.30.2` の全 crash 性質や、このアプリの multi-table atomicity の実証ではない。

コード上、MCP / HTTP startup は `strictMaintenanceLock()` → `acquireShared()` → read-only strict diagnostic → writable `DBEngine.connect()` → listener / watcher 起動の順で進む。writable connect は embedding identity の確認後、`init_tables()` で不足 table と scalar index を作る。通常 startup はこの変更区間を `exclusive` / `incomplete` で囲んでいない。scalar index 作成の例外は警告を出して続行する。

**既存の実測:** disposable DB で必要 table を残したまま `index_requests.status` index 作成を失敗させた試験では、行数・logical row hash・対象 filter 結果は一致し、read-only strict diagnosis も通り、次回 `init_tables()` で index が作成された。これは試験用 DB / 5,000行での一回の確認で、性能 benchmark や native API 内停止試験ではない。q4 の「起動時 scalar index 作成を維持する方向」と整合し得るが、欠落 index を readiness 上どう見せるかは決めていない。

**既存の実測:** 3秒に短縮した隔離 heartbeat lease が失効し、新 Watcher が `WATCHING` になった後、接続を維持した旧 DBEngine client から request を1件保存できた。旧 client は active Watcher loop ではない。従って lease を lock / fencing と同一視できず、active writer 二重化の安全性やデータ破損を示した結果でもない。

**コードからの推論:** lock directory 作成 (`gate`, `users`, `exclusive`) と `identity` 書込みには明示的な directory/file fsync が見当たらない。`incomplete` の作成・除去は parent directory sync を行う。SIGKILL 試験は OS crash / 電源断の永続性を証明しない。single-host は multi-host 非対応を定めるが、同じ host の container/mount、共有可能な filesystem、atomic `mkdir`・path identity・directory sync の性質までは自動的に定まらない。

### crash 時に「正常」と言える根拠

次の表は現行挙動と、inq-15 の意図を実現するなら必要になる概念上の区別を並べたもので、状態名・marker・遷移は未承認。

| crash / failure point | 現行の残存状態・後続起動 | 次の利用者が必要とする情報 |
|---|---|---|
| shared registration / `gate` の作成途中 | gate や空 UUID directory が残り得る。owner 情報がなく、lock API は fail-closed | admission が止まる理由、どの marker があるか。process owner / stale を確定した表示はできない |
| 通常 startup の writable DB init 中 | `users` は既にあるが `exclusive` / `incomplete` はない。必須 table が不足すれば strict startup は拒否。必須 table が揃い scalar index だけ失敗すれば strict は通り、初期化を再試行し得る | DB init が完了したのか、必須要件だけ満たし任意 index が不足するのか、同時 startup とどちらが初期化中か |
| exclusive 作成後・不安定 marker 作成前 | `exclusive` が残れば shared を拒否。marker がなければ operation / phase は分からない | 作業開始前か、marker 書込み前に DB を変更したか。現行 lock record だけでは判別できない |
| persistent unstable marker 後・DB 変更前 | 現行 maintenance なら `exclusive + incomplete`。通常利用は拒否し、実際には DB が未変更の可能性もある | どの段階まで進んだか、再開可能か。これを推定で `READY` に戻さないための明示診断 |
| DB / schema / index 変更途中 | maintenance なら `exclusive + incomplete`; 普通の startup init では同じラッチがない | DB の部分状態・検査結果・復旧選択肢。marker の存在だけで破損の種類までは分からない |
| rebuild / migration のデータ検証後・marker 完了前 | marker が残れば正常 DB に戻っていても通常利用は拒否 | 検証済み内容と未完了の最後の遷移。完了 marker clear の順序と耐久性 |
| marker 完了後・exclusive release 前 | DB は検証済みの可能性があるが exclusive が残れば利用不可 | ready record と残存排他を別に提示する情報 |
| q9/12 の child stop 未確認後 | 親は失敗終了し共有登録を残す方向。inq-11 は同一 identity の新しい shared 起動を許す | child stop unconfirmed の事実と子の種類。共有登録単体はその情報を保持しない。ここを q15 の lock が止めるのか、利用者判断に委ねるのか未確定 |

未検証の破損や未知の旧 DB を `UNSTABLE` / `READY` のどちらかへ推測で分類するのは危険である。必須 table 欠落・read error の fail-closed は既存観測があるが、すべての部分破損を識別できるわけではない。特に “marker がない” は旧 DB / 正常 DB / marker を書く前の crash を区別しない。`embedding_identity` はモデル・次元の互換確認で、DB format / schema version ではない。

### 全体を簡素にする設計候補

設計上の推奨は、**通常利用と例外復旧を二つの経路に分け、利用者が判断に必要な状態を一つの読み取り専用診断で見られるようにすること**。ただし保存方式、既存 lock の用途拡大、公開 API、復旧操作はまだ決めない。

概念状態の候補:

- **`READY`**: 互換性と必須構造の検査が通り、通常利用を開始できる。scalar index だけ不足する場合は data integrity failure と混同せず、`READY_WITH_WARNING` 等の degraded 情報を出す案を検討する。q4 の既存作成方向と、一回の filter/hash 実測には整合するが、warning をどこに出すかは未決。
- **`TRANSITION`**: 初期化・migration・保守など、storage を変更する一つの operation が排他下で進行中。利用者には「処理中」と分かるようにし、通常検索・writer admission とどう共存させるか決める。
- **`RECOVERY_REQUIRED` / `UNKNOWN`**: operation の中断、lock / marker 不整合、破損・未知 format 等で ready を証明できない。自動で lock / marker を消さず、status と候補 recovery を表示して通常利用を止める方向を提案する。これは q11 の同一 identity 起動許可との整合判断が必要。

最低限利用者へ渡す情報の候補は、status とその根拠（必須 table・embedding identity・scalar index・heartbeat / writer state の個別成否）、現在/最後に確認した operation phase、最後の error、残る `gate/users/exclusive/incomplete`、検査を行った時刻、復旧可能な候補とその破壊性。timestamp や PID は参考情報にとどめ、process が生きている/死んでいる証拠として出さない。未検証事項は `UNKNOWN` として表示する。MCP / CLI / HTTP のどの surface と schema に載せるかは決めない。

| 選択肢 | 何を守れるか | 反例・移行負担 |
|---|---|---|
| **A. 現行 admission を維持し、診断情報だけ増やす** | 既存の複数 same-identity shared 利用と 5 MCP startup 経路を保ちやすい。例外状態の説明は改善できる | startup `init_tables()` は shared 中に DB を変更するため、初期化期間を lock で保証できない。status だけでは排他の穴を埋めない |
| **B. 既存 `exclusive` と persistent incomplete-state を状態遷移の基礎として使う** | 新しい lock 名を増やさず、変更前に例外期間を立て、DB 検証後にだけ通常状態へ戻す概念が最も小さい。crash 後は不安定状態を残せる | 現在の startup は shared 登録後に table/index を変更するため、exclusive-before-shared の初期化 / ready への切替を設計変更する必要がある。既存 5 MCP parallel-startup を維持するには、最初の initializer と待機側を競合で失敗させず直列化する入口が必要。incomplete は実際の破損だけでなく pre-write crash にも立ち、owner / phase 情報がない。marker semantics 拡張は未承認 |
| **C. versioned readiness / format manifest と operation phase を追加** | 状態、format、operation、last error を構造化して読める。旧 format / migration の境界を明示しやすい | 永続 marker と Lance table の間の二資源 crash window、旧 DB の adoption / migration / rollback / 古い client compatibility、format durability が増える。新しい永続状態であり未承認 |
| **D. heartbeat または MVCC に例外期間の lock を代行させる** | storage 内の現状を観測する材料にはなる | heartbeat lease は old client write を fence せず、MVCC は app 全体の初期化や maintenance admission をしない。観測した範囲では lock の代替にならない |

**推奨:** 実装決定ではなく、まず B の論理モデルを基準に試験可能な設計を作る。つまり通常経路は「必須条件が確認できた状態」だけを ready とし、変更を伴う一つの operation は明示的な排他期間に入り、成功時は read-only 検証を通してから ready に戻る。途中終了は recovery-required / unknown のまま利用者に見せ、timeout・PID・heartbeat だけで勝手に完了扱いしない。これなら個別 UUID を並べて削除するのを通常の exception UI にせずに済む。

ただし B は今の実装に対する変更を伴う。特に「5 MCP が新規 project に並列起動する条件」を維持するなら、初期化担当が lock を取るまでの待機・他プロセスの再検査・失敗 deadline を決め、成功試験を要する。さらに inq-11 の「child 停止未確認でも同一 identity の通常起動を許す」選択は、`RECOVERY_REQUIRED` が全 shared start を止めるモデルと両立しない可能性がある。inq-15 がこれを変更したとは扱わない。

### simple exception recovery の全体像と適用限界

個別 UUID の削除順を利用者に選ばせるのを既定にせず、例外経路は次の高レベルフローに集約する案を推奨する。これはコマンドも許可条件も未承認で、現行 code でそのまま実行できる手順ではない。

1. **状態を読む:** read-only diagnostic が path / identity / format の識別、必須構造、embedding identity、任意 index、maintenance marker、各診断の失敗をまとめる。診断が完遂できない時は `UNKNOWN` とし、正常と推定しない。
2. **通常利用を止めて保全:** recovery は明示操作とし、対象 storage を開く全 process / child / restart source が止まり、同一 host の利用実態・storage identity が確認できる条件を置く。single-host 方針から既存利用者や filesystem 性質を推測しない。data backup があるとは仮定せず、検証前に復元可能とも表示しない。
3. **回復経路を選ぶ:** q3 の方向に沿う候補は (a) 現在の authoritative source から全再構築、または (b) 同じ recovery point の `index` + `documents` を対にした正常 backup の restore。partial table を自動で作って埋めない。source の欠落・embedding provider 不調・backup の世代/完全性/format 不明ならその場で拒否する。
4. **排他中に検証する:** 両データ領域の整合性、必須 table / embedding identity / relevant indexes、read-only strict diagnosis を確認し、完了記録を最後に確定する。restore だけでは `incomplete` を解除しない。どの結果・証跡で marker を clear できるかは決定が要る。
5. **通常利用へ戻す:** ready 記録と排他 release の順序を一つの状態遷移として定義し、落ちた場合も read-only status が不一致を報告できるようにする。

現行では stale `gate` があると gate 取得に依存する操作は失敗し、stale `users` があると exclusive は拒否され、stale `exclusive` は shared / maintenance を止める。従って上のフローへ入る admission 自体がふさがる場合がある。これを解消する案には (i) 利用者が実利用全体を停止した保守時間帯で対象 control state を明示的に回復する、(ii) offline maintenance entrypoint を作る、(iii) management control area をまとめて初期化する、がある。どれも対象範囲・破壊性・状態保全が異なり、とくに (iii) は operator が承認していない。今回その操作はしていないし、既定案にもしていない。つまり、**現行の個別手動案を既定にしないだけでは stale gate/exclusive/users から復旧する具体経路は生まれない**。ここが設計上まだ解けていない根本の限界である。

### 実装前の decision と試験計画

conductor に operator decision として返す論点:

## operator decision inq-17: 通常 MVCC と不安定操作を分ける（2026-11-28）

operator の決定を原文どおり署名付きで [Issue #183 に記録した](https://github.com/otolab/search-docs/issues/183)。inq-17 は q15 の「不安定な時間を排他で保証し、使う側が状態を判断できる情報を増やす」と q16 の read/write の分岐を、次の分類から設計する選択である。

> 既存 schema 上の query・通常 row-level MVCC write を正常利用、DB 初期化・構造変更・再構築／復元・物理 pruning を不安定操作とする区分を設計の出発点とする。

これは、periodic optimize の実行時期、scalar index の起動時作成と失敗処理、legacy DB adoption、reader admission、lock・永続 marker の具体形や実装を決めていない。scalar index 作成は構造変更に見える一方、inq-4 の startup 維持方向があるため、q17 の category をそのまま適用する前に扱いを決める。周期 optimize も physical pruning を含み得るが、現行は共有 writer の20回ごとに呼ばれる。どちらも判断保留とする。

### ひとつの論理状態遷移

以下の `NORMAL` / `UNSTABLE` / `UNKNOWN` は設計比較用の概念名であり、現行 API の status、marker、lock 名ではない。

| 段階 | 作業と利用可否の候補 | 利用者に示す証拠 |
|---|---|---|
| **Read-only preflight** | DB / source を変更せず、storage identity、table 一覧、schema、embedding identity、既知の transition evidence を調べる。起動中の writer はまだ開始しない | 実際に読めた値と未確認項目を分ける。現行 `diagnoseStrictConfig()` は必須 table の読出し、heartbeat、文書 path と index の整合などを調べるが、DB format version・全 table schema・scalar index readiness を網羅していない |
| **NORMAL** | 既知の schema 上で query と通常 row-level MVCC write を行う。heartbeat は writer の選出情報で、stale writer を fence した証拠にしない | 必須 table / identity 等の検証結果と、scalar index の有無・状態は別に表示する候補 |
| **UNSTABLE** | DB 初期化、構造変更、rebuild/restore、物理 pruning を行う期間。候補遷移は「排他の取得 → mutation 前の transition 記録 → mutation → read-only verification → 完了状態への移行 → 排他解放」。どの lock/marker を使うか、reader を止めるか、shared registration からどう handoff するかは未決 | operation と確認できた phase / 時刻 / DB identity を表示する候補。record が耐久化されていると証明できない場合、phase を確定扱いしない |
| **UNKNOWN / RECOVERY REQUIRED** | legacy・部分 DB・恒久欠落・途中停止を区別できない状態。通常 writer は開始せず、read-only diagnosis と明示 recovery の案内に限定する候補。自動補完・自動回収はしない | table / identity / marker の観測事実と、owner / child 生存が `UNKNOWN` であることを別々に示す。marker がないことや lease expiry から正常・所有者不在を推定しない |

この順序では、mutation が起き得るより前に状態を記録できることが安全条件になる。ただし現在の `gate` は短い登録調停、`users` は利用中登録、`exclusive` は maintenance 排他、`incomplete` は一部 maintenance の完了状態であり、起動初期化の durable phase record ではない。`incomplete` は directory sync を行うが、他の registration path と DB 側状態の耐久性は同等と確認されていない。新 marker の導入や既存意味の拡張は未承認で、単一 host という決定だけでは filesystem の atomicity / durability も確定しない。

### 起動・中断・復旧を一続きにしたシナリオ

1. **既知の既存 DB:** read-only preflight が許容済み format / schema / identity を確認できた場合だけ `NORMAL` 候補に進み、query と row-level writer を始める。現行起動は shared registration の後に writable `connect()` / `init_tables()` を実行するため、初期化が必要となったときに shared 利用者から排他へ移る順序と、5 MCP / 30秒以内の同時 startup 待機を設計し直す必要がある。
2. **新規 DB または承認済み構造操作:** `UNSTABLE` に入り、required tables / identity / schema の作成や承認済み maintenance を実行し、読取専用診断で完了を検証してから初めて writer を `NORMAL` にする。開始前の crash、transition 記録後・mutation 前、各 table/index の作成途中、mutation 後・verification 前、verification 後・記録 clear 前、clear 後・排他 release 前を別 crash point とする。途中で停止したときは、永続証拠が足りなければ `UNKNOWN` に留める。
3. **起動時 scalar index 欠落 / 作成失敗:** required table / row の欠落とは混同しない。現行 `init_tables()` は不足 index の作成を試し、例外を warning にして続行する。inq-4 の維持方向と q17 の構造変更区分を両立するには、(a) 初回 index 作成を短い `UNSTABLE` として startup を直列化し、失敗時は transition を保持して起動を止める、または (b) table / row readiness と index readiness を分け、検索・row write は warning 付きで許し、index 作成は後続の明示 `UNSTABLE` に回す、などの決定が必要。失敗後も起動を正常扱いする現在の経路を黙って維持することも、全 DB を壊れた扱いにすることも決めていない。既存の5,000 row disposable index failure 試験は row/hash/filter 不変を確認したが、性能・実サービス concurrent startup・crash safety は未検証。
4. **20 write 周期の `optimize(cleanup_older_than=10分)`:** これは現在 shared writer 内にある一方、q17 では physical pruning は不安定操作に分類される。選択肢は、周期ごとに排他 transition と waiter/handoff を行う、pruning を explicit maintenance に分離して通常 writer は MVCC row write に限定する、または共有中の実行を carve-out として許す、の三つ。最後の案は q17 の出発点に例外を設け、reader safety を別途許容する判断になるため、既定にしない。no-checkout 10分 run では seed version が消えた一方、cleanup 後窓の query 件数を保存できず、Python call overlap は1回で native overlap を示さない。raw pinned reader の `Not found` もあり、reader を許す安全性は証明されていない。
5. **既存の旧 format / marker のない DB:** application format version がないため、見た目の table 一覧だけでは互換な旧 DB と一部初期化後の停止を確実に分けられない。read-only で識別可能な legacy fingerprint による明示 adoption、versioned migration、`UNKNOWN` として full source rebuild / verified backup restore を案内、を比較する。既知でない DB を自動 adoption / 補完しない。q3 の rebuild / backup 基本経路は、元文書の完全性、backup と文書 storage の対応、restore 後の検証、`incomplete` を解除する条件までは決めていない。
6. **不安定中の crash と operator recovery:** read-only diagnosis は既知の残存 marker / tables / identity / version とその欠落を報告し、owner / host / child が確認できなければ `UNKNOWN` とする。自動の DB 補完・stale state 除去・backup restore 成功だけでの transition clear は行わない候補。利用者が選ぶ recovery は、全利用者・child 停止と新規起動の停止を確認した上で、元文書からの全再構築か、適合性を確認した backup の復元とする。復元後は document/index の対応、required tables・identity・schema、必要な検索、index status を検証する。ただし scalar index failure をどこまで受容するか、どの証拠で `incomplete` を clear するかは未決。stale `gate` / `exclusive` で通常 recovery admission が拒まれる場合の入口も決まっておらず、q13 の人間確認条件を満たせない場合は処置せず停止する候補である。

diagnostic では DB readiness と child/process cleanup を別軸にする。inq-9/10/12 の停止未確認時の親終了・登録保持と、inq-11 の同一 identity 通常起動許可はそのまま維持し、child が残る可能性を DB の `NORMAL` 証拠にも自動的な `UNSTABLE` 判定にも流用しない。ただし残存 child の DB access 能力が未確認なら、DB を利用する safety claim は `UNKNOWN` として出す必要がある。

### 次に不可欠な operator 判断（2点）

1. **既存自動 mutation と transition 中の admission。** periodic optimize は不安定操作としてどこで実行するか（20回ごとに排他する / explicit maintenance へ移す / shared operation 中の例外を明示承認する）。scalar index は、startup 直列化して作成し失敗時に止めるか、index readiness を分けて通常利用を warning 付きで続け作成を後回しにするか。実際の physical pruning・schema/table mutation 中に read-only query を許すかもここで決める。推奨は、row-level MVCC は `NORMAL` のまま、physical pruning と scalar-index creation は一旦 `UNSTABLE` 扱いにし、reader admission の証拠が得られるまでは共有利用を許さない設計から比較すること。代償は periodic cleanup のたびの待機・startup latency と、既存5 MCP/30秒条件の handoff 設計である。
