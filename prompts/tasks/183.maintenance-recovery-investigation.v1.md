## 複雑さと懸念

- **複雑度は高い**。filesystem 上の短命な排他登録と DB 内の MVCC / heartbeat が別の資源・別の寿命を持つため、単一の「lock がある / ない」では起動中断の安全性を説明できない。ファイル作成と fsync の間、DB schema 初期化と read-only 診断の間、writer claim と shutdown の間を分けて追う必要がある。
- `gate` / `users` は保守ロックと共有利用の間を調停する。一方、heartbeat は writer の選出であり、全 DB 書込みや DB 初期化完了を保証するものとは限らない。MVCC も操作の隔離・snapshot の性質を確認する対象であり、起動の準備完了やロック所有者の生存を自動で証明するとは仮定しない。
- crash や破損を再現する場合は、必ず新規一時領域か複製 DB を使う。実利用データを変更・削除せず、試験後の状態と cleanup の成否を記録する。
- ローカル単一ホスト・ローカル filesystem の試験から、共有 / network filesystem、multi-host、Windows を含む挙動へ一般化しない。未試験範囲として明示する。
- 部分初期化 DB と既存 DB の恒久破損を判別する根拠がないまま、欠損を無視したり自動作成したりしない。
- 制御試験が現在の lock を通過したことを、現行方式の維持や回収方式の承認として記録しない。

## 現行コードから分かる制御範囲

### 実装上の順序

- MCP / HTTP の通常起動は `gate` の中で共有登録 (`users/<UUID>`) を作り、その後 gate を解放する。サービス起動側は共有登録を保持したまま strict 診断を行う。
- MCP の strict 診断は embedding server / DBEngine の起動前に実行される。診断は read-only DBEngine を `skipInitModel` で接続し、heartbeat と索引・保留 request のパス、文書コピーを確認する。
- strict 診断後にサービス側が DBEngine を writable で接続する。Python worker は provider/model を確認し `embedding_identity` を作成した後、`sections`、`index_requests`、`writer_heartbeat` を順に作り、scalar index を管理する。writer の claim は `connect()` 成功後に始まり、claim 後の `beforeWriter` でも strict 診断を行う。
- `init_tables()` は table 作成失敗を伝播する一方、個々の scalar-index 作成失敗は警告を出して継続する。従って「init_model が成功した」ことは、必ずしも全 scalar index の作成完了を保証しない。
- `gate` は `mkdir` の排他で shared registration と exclusive acquisition の短い判定・更新区間を直列化する。`users` は shared利用の継続中、`exclusive` は破壊的保守中、`incomplete` は保守未完了を示す。いずれもプロセス所有者を記録しない。
- LanceDB の heartbeat は writer 選出に使う。コード上、起動前 strict 診断・`embedding_identity`・全 table の作成や maintenance gate の代替にはならない。heartbeat 自体の読み書きも DB worker の操作であり、全テーブル横断の transaction ではない。
- `markIncomplete()` は親ディレクトリと管理ディレクトリを fsync するが、gate / users / exclusive の作成・削除と identity file の書込みには明示的 fsync がない。SIGKILL 試験はプロセス強制終了後の状態を示すもので、OS crash / 電源断時の耐久性は実証しない。

## 隔離した制御試験の結果

### gate / users / exclusive / incomplete

実行条件: 現行 `maintenance-lock.ts` を一時ディレクトリへ複製し、テスト専用 pause hook を複製側だけに挿入。独立した Node プロセスを SIGKILL で停止した。製品ソースは変更していない。

- `gate` 作成直後に SIGKILL: `gate` が残り、shared の再取得は1秒の待機後に残存 gate として拒否された。試験用領域で gate だけを手動除去すると shared / exclusive のどちらも取得できた。
- user directory 作成後・identity 書込み前に SIGKILL: `gate` と空の user directory が残った。試験用領域で gate を除去後も、shared は identity を読めず拒否され、exclusive は user directory が残っているため拒否された。
- identity 書込み後・gate 解放前に SIGKILL: `gate` と identity 付き登録が残った。gate のみ除去すると同じ identity の shared は追加できたが、別 identity は拒否され、exclusive は既存 user により拒否された。
- 同じ一時領域上で shared と exclusive の別プロセス取得を20回同時に開始: 各回で片方だけ成功し、両方成功または両方失敗はなかった（shared 10回、exclusive 10回）。これは単一ホスト・ローカル filesystem・この実装の短い制御競合の試験に限る。
- exclusive 取得後・`incomplete` 作成前に SIGKILL: exclusive が残り、shared は拒否された。試験用領域で exclusive を手動除去すると shared / `requireComplete` 付き maintenance は取得できた。
- `incomplete` 作成後に SIGKILL: exclusive と incomplete が残った。試験用領域で exclusive を除去しても shared と `requireComplete: true` の maintenance は拒否された。`requireComplete` を指定しない内部 lock API なら排他を再取得し `incomplete` を維持したまま処理後に clear できたが、これは operator-facing な復旧仕様の承認・検証ではない。CLI force-repair と MCP purge は `requireComplete: true` を使う。

### DB 初期化と通常再起動

実行条件: 新規の一時プロジェクトと DB ごとに Python worker の一時複製へ pause hook を挿入し、次の境界で worker を SIGKILL した。Embedding は `/health` 応答だけの loopback fake server で、推論は行っていない。read-only strict 診断の前後で DB tree 内の全ファイル名・内容 hash を比較した。

| SIGKILL 境界 | kill 直後に見えた DB | strict 診断 / hash | MCP 通常再起動 |
|---|---|---|---|
| `embedding_identity` 作成後、必須 table 前 | identity のみ | heartbeat 未作成で拒否 / 不変 | MCP initialize 前に終了 |
| `sections` 作成後 | identity + sections | heartbeat 未作成で拒否 / 不変 | MCP initialize 前に終了 |
| `index_requests` 作成後 | identity + sections + index_requests | heartbeat 未作成で拒否 / 不変 | MCP initialize 前に終了 |
| `writer_heartbeat` 作成後 | identity + 必須3 table、index なし | 診断合格 / 不変 | 起動成功。再初期化で scalar index がそろった |
| index_requests の status scalar index 作成後 | 必須 table + status index のみ | 診断合格 / 不変 | 起動成功。再初期化で残りの scalar index がそろった |

- 先の3ケースでは、strict 診断後の「通常 MCP 起動」は DBEngine の writable `connect()` に到達せず終了した。一方、同じ一時 DB に strict gate を介さず `DBEngine.connect()` を直接行うと、いずれも残りの table と index が作成され、接続に成功した。これは現行初期化処理が部分状態を継続できることを示すが、通常の MCP 経路ではその処理に到達できない。
- 必須 table がそろった後の scalar-index 初期化途中は、strict 診断を通過し、通常 MCP 起動が不足 index を作成して成功した。
- ここでいう SIGKILL は `init_model` の identity/table/index 作成境界に pause した worker を止める試験。`create_table` / `create_scalar_index` の native 処理の途中で kill した試験ではない。
- hash 比較は各 partial-init DB への read-only strict 診断前後では一致した。既存 DB 破損・欠落を修復する処理も診断経路にはなかった。恒久欠落と内容破損も、別の一時 DB で独立に試験した。

### writer 昇格中の shutdown、恒久欠落・破損 DB、起動回帰

- **writer 昇格中の SIGTERM（実測）**: 一時プロジェクトの MCP プロセスを起動し、writer 前の2回目の strict 診断で停止するよう生成済み server bundle の一時複製に pause を入れた。診断用 Python process group が生存中に親へ SIGTERM を送り、診断を再開した。親は診断中には終了せず、再開後に exit 0。Python process group は停止し、`WATCHING` ログなし、heartbeat 0 行だった。fake embedding server は `/health` のみ返し、推論なし。生成物への一時計測は試験後に元へ戻した。
- **5 MCP 起動回帰（実測）**: `parallel-mcp-startup.test.ts` を実行し、新規一時プロジェクトで5プロセスが30秒以内に接続、exclusive を拒否、起動中 SIGKILL 後に再接続する1テストが6.2秒で成功した。workspace root にだけ Vitest があったため package filter 経由では runner を見つけられず、root の Vitest binary を直接呼び出して実施した。
- **DB connect 後・identity 前（実測）**: instrumentation を `Path(db_path).mkdir()` と `lancedb.connect()` の直後に置いて worker を SIGKILL。DB path は存在するが table 0。strict は missing heartbeat で失敗し snapshot 不変、通常 MCP も initialize 前に exit 1。strict を通さず同じ DB に直接 `DBEngine.connect()` すると初期化完了した。
- **恒久欠落 table（実測）**: 完成済み一時DBから `writer_heartbeat` を除いた。strict 診断は `Table 'writer_heartbeat' was not found` で失敗し、前後 snapshot hash は不変。通常 MCP も exit 1、DB hash 不変、users 登録なし。
- **Lance data file 破損（実測）**: 完成済み一時DBの `writer_heartbeat` data file をゼロで上書きした。strict は Lance file の invalid magic error で失敗し、診断・MCP 起動の前後で DB snapshot hash 不変、MCP exit 1、users 登録なし。破損データを隠す自動修復はなかった。
- 上記欠落・破損試験も一時 DB 限定。実利用 DB には触れていない。snapshot はファイル一覧と内容 hash。新規一時環境での再現であり、電源断・OS crash・native table write 中断の試験ではない。

## crash-point matrix

| 停止点 | disk / 登録に残る実測状態 | 通常起動・保守の現行挙動 | 回復上の含意 |
|---|---|---|---|
| `gate` mkdir 直後 | 空の `gate` | 1秒後 gate 使用中として失敗 | process owner が記録されない。全利用停止確認後の手動除去が必要 |
| `users/<uuid>` mkdir 後、identity 前 | gate + 空 user dir | gate 除去後も shared は identity 不在で失敗、exclusive は user count > 0 で失敗 | 作成途中か壊れた登録かをコードだけで識別できない。手動確認が要る |
| identity write 後、gate 解放前 | gate + 有効 user 登録 | gate 除去後も登録は共有利用中として残る | shared 登録の内容だけでは所有 process の生存を証明できない |
| exclusive mkdir 後、`incomplete` 前 | `exclusive` | shared と次の exclusive を拒否 | 変更前でも人手の排他回収が必要になる |
| `incomplete` 作成後、処理 / complete 前 | `exclusive` + `incomplete` | shared は拒否。force-repair / purge (`requireComplete:true`) も拒否 | 明示全再構築 `index recreate` は `requireComplete` を渡さず再試行可能。ただし stale `exclusive` / `users` があれば先に人手確認が必要 |
| DB path 作成・LanceDB connect 後、embedding identity 前 | 一時 DB directory のみ、table 0 | strict は missing heartbeat で拒否し、通常 MCP は接続前に終了。strict hash 不変 | `DBEngine.connect()` を strict なしで直接実行すると初期化成功。通常経路はこの再開に到達しない |
| embedding identity / 必須 table 作成途中 | identity と table の一部 | strict 起動は missing required table で拒否し、書込みなし。strict を迂回した DBEngine 初期化なら残りを作る | 部分初期化と恒久欠損を通常起動が区別できない。迂回を製品動作に採用する判断は未承認 |
| 必須 table 完了後、scalar index 作成途中 | 必須 table、一部 index | strict 合格。起動時の再初期化が不足 index 作成を試みる | index 作成 error は警告継続のため、全 index 完了の保証にはならない |
| strict 診断中（writer 前）に SIGTERM | 診断 subprocess が生存する間は親が終了を待つ | 実測では診断再開後に clean exit、writer heartbeat なし | 試した診断 pause point に限る。SIGKILL / 電源断の子孫停止保証ではない |
| 必須 table の恒久欠落 / data file 破損 | 一時 DB 内に欠損 / invalid file | strict と MCP が fail-closed。read-only 診断前後 hash 不変 | 通常起動は復旧しない。バックアップ復元か、明示的な全再構築候補 |

## MVCC / heartbeat / filesystem 登録の守備範囲

- **実装上の事実**: Python worker は read-only 接続に `read_consistency_interval=5秒` を設定する。heartbeat 読取は別の新規 DB 接続から行う。writer heartbeat は writer election / 活動状態の共有に使われる。strict 起動診断は DBEngine を read-only + `skipInitModel` で開く。`gate/users/exclusive/incomplete` は DB とは別の filesystem 管理領域。
- **公式 API の説明**: LanceDB の `read_consistency_interval` は他 process の table 更新を確認する read 用の設定で、write は常に consistent とされる。LanceDB の version history は table ごとに write commit を記録する。([Python API](https://lancedb.github.io/lancedb/python/python/), [Tables / Versioning](https://docs.lancedb.com/tables/versioning))
- **コードからの推論**: アプリ初期化は embedding identity、3 required table、scalar index を順に別呼出しで作る。DB-wide transaction または全 table の一括 commit/version marker は見当たらない。従って Lance の table MVCC は各 table 内の read/write 世代には関わるが、アプリ全体の複数 table 初期化を一括 rollback したり「初期化完了」を証明したりしない。table create / index build の内部で crash した場合の Lance 回復性は今回未試験。
- **コードからの推論**: heartbeat の存在や更新は writer 選定の材料であり、DB format compatibility、全必須 table の初期化完了、maintenance 状態の修復、filesystem lock owner の生存証明ではない。
- **調査範囲**: `format_version` / `schema_version` / DB version table / migration framework はアプリの db-engine / CLI source に見つからなかった。`embedding_identity` は provider / model / dimension の一致確認であり、schema version や初期化完了 marker ではない。これは検索範囲に基づく結論で、依存ライブラリ内部の format metadata が無いという主張ではない。
- **未実測**: LanceDB の複数 table にまたがる transaction semantics、OS crash / power loss と fsync 永続性、network/shared filesystem、multi-host、Windows は検証していない。SIGKILL はこれらの proxy ではない。

## 回復候補と限界（採用判断ではない）

| 候補 | 利点 | 主な限界・必要な判断 |
|---|---|---|
| 現行の fail-closed + 明示 `index recreate` | 新たな永続状態を増やさず、source からの全再構築という既存経路で `incomplete` を再試行できる。確認・隔離・保存先検査とマーカーを使う | 全 index を作り直す破壊操作で、元文書が再取得可能でなければ復旧できない。stale gate/exclusive/users の自動回収はしない。table 単位 repair / purge は incomplete を拒否 |
| 自動 stale lock 回収 | gate などの放置で起動不能になるケースを減らす | 現行 dir に PID / host / start token がなく所有者を判定できない。PID/lease だけでは PID reuse、複数 host、停止中 process、fencing の問題が残る。heartbeat は別資源の writer election で代替根拠にならない |
| DB 内 init-ready marker | partial-init と ready DB を区別する足がかりになる | marker 自体の作成・更新順序と durability が要る。同じ DB に置くと途中作成 / 破損時の意味を定義する必要がある。外部 marker は DB と二資源になる crash window と identity binding が生じる |
| DB format version + migration | 将来 schema の識別と移行経路を明示できる | 現状 framework がない。migration の順序、再実行安全性、途中失敗、旧版互換・backup・downgrade を別途決める必要があり、version 値だけで ready を保証しない |

### multi-host 前提と試験限界

`strictMaintenanceLock()` は標準の兄弟配置、symlink でない directory、local path の `realpath`、親と index/documents/management の `st_dev` 一致を検査する。実 lock は共有 path に対する `mkdir` と directory marker であり、`gate/users/exclusive` に owner host / PID / start time / fencing token はない。これらの確認は同一ホスト内の配置検査であり、複数 host 間の原子性・可視性・partition 時の排他保証を証明しない。

本環境には独立した第二 host と、製品運用対象として指定された shared/network filesystem がないため、multi-host の同時取得・network partition・NFS/SMB のキャッシュ反映・host reboot・lease fencing は実施できない。従って前回の20回 raceも今回の試験も multi-host の証拠ではない。明示的復旧の安全条件としては「到達できる全 host、旧 version、process descendants、直接 DB access の停止確認」と「全利用者が同じ management directory を見ている確認」が必要だが、接続不能 host の不在はこの環境から検証できない。

**operator decision（inq-1）**: 対象は単一 host とし、複数 host での利用は非対応と明記する。この決定で multi-host 対応の検討は今回の対象外になるが、filesystem の種類や同一 host 内の複数 process の調停条件まで決まったわけではない。

単一 host の範囲でも、協調する全 process が同じ実体の DB path と management path を参照し、管理領域上の directory `mkdir` が競合時に原子的に一方だけ成功すること、作成・削除が他 process から適切な時点で見えることが必要になる。`st_dev` の一致と `realpath` は配置の一部を検査するだけで、これらの意味や障害後の永続性を証明しない。特に別 host からも同じ shared/network filesystem に接続できる構成は、製品としては非対応である。shared/network filesystem を単一 host だけが使う構成の対応可否も、今回のローカル一時 filesystem 試験からは判断できず、運用対象の filesystem を指定した追加検証が必要になる。

### conductor への選択肢・帰結・推奨

1. **保守と利用 client の契約**: (a) `users` を全協調 client lifetime に使う、(b) reader 等の登録を減らす、(c) OS / coordinator lock に置換する。 (a) は破壊的保守中に reader も止める現在の保証を保つ一方 stale directory を手動確認する。 (b) は利用 client が見えなくなるため、読者と destructive maintenance の重なりを許せる根拠が必要。(c) は全参加者の移行と各 filesystem / platform の試験が必要。**推奨**: どの利用者を maintenance から守る必要があるか決めるまで `users` を弱めない。これは現在の機構自体を採用する決定ではなく、保護対象を未定義のまま削らないための順序提案。
2. **partial DB の recovery target**: (a) current source が取れる時の全 recreate、(b) 同じ世代の backup による index + documents restore、(c) strict を迂回した writable init の継続、(d) explicit maintenance recovery を新設。今回 (a) は partial DB + incomplete から source がある場合に成功し、source 無しでは hash を保って拒否。(b) はDB診断を回復したが incomplete は別途残った。(c) は現在のDBEngineが不足 table を作れるだけで、破損と partial を区別しない。(d) は仕様設計が必要。**推奨**: automatic continuation を採らず (a)/(b) の適用条件と管理 marker の正式な回復手順を決める。backup restore を用意する場合、index と documents の同世代性、backup integrity、format compatibility、stale management markers の扱いを定義する。
3. **format / writer start**: (a) marker なしで strict fail-closed、(b) new-empty-only initialization、(c) format-versioned resumable migration + ready marker、(d) explicit maintenance からだけ復旧。 (a) は既存状態を増やさないが自動継続しない。(b) は初回識別と startup race が要る。(c) は version互換・再実行/rollback・durability が要る。(d) は手動介入と新 command 仕様が要る。**推奨**: strict を迂回して欠損 table を作る案は採用しない。自動復旧を必須とするかを決め、それが必要な場合に readiness/version の commit point と旧 DB 移行契約を先に設計する。
4. **host の対応範囲（inq-1 決定済み）**: operator は (a) 単一 host を対象とし、複数 host は非対応と明記する案を選択した。これは multi-host support を今回の要件に含めない決定である。shared/network filesystem を単一 host から使う構成まで対応と認めたわけではない。**未決定の前提**: 同一 host 内の全協調 process が共通の DB / management path を使うこと、filesystem 上の `mkdir` 原子性と directory 更新の可視性、必要な永続性、および別 host からの同じ領域へのアクセスを運用上排除できること。今回確認したのは macOS の単一 host / local temporary filesystem に限られ、NFS/SMB 等の保証はない。
5. **停止未確認の扱い**: 今回の実サービス fault 試験では parent MCP は exit 0 でも diagnostic child process group が残り、registration を残したことで exclusive が拒否され writer も開始しなかった。lock 実装の採否とは別に、停止未確認時に同等の排他を保つ必要性は実測された。**推奨**: 代替する場合も、残存 child がいる間に destructive maintenance を許さない同等条件を設計・試験する。

この報告時点では Issue #180 の本文・受け入れ条件を編集せず OPEN のままとした。5 MCP 並列条件は reviewer が実 LanceDB / fake health で6.585秒の再検証をしたが、SIGKILL 点は writable DB initialization より前である。今回の partial-init と fault harness が受け入れ条件の全 crash point を満たしたとは扱わない。

- `cleanup-failure.mjs` は child 起動後に意図的な失敗を起こす。最終確認では child の `SIGKILL` 終了と close 後の temp root 削除を assertion で確認した。

開発中に一度 cleanup helper の import 漏れで harness が temp root を保持した。記録された2つの process group は `kill(pid, 0)` が `ESRCH` であることを確認し、該当する使い捨て root だけを削除した。import と registry の newline 処理を直した後の全実行では cleanup が通っている。

### 追加した crash matrix と最終実測

`recreate-recovery.mjs` は一時複製 worker / provider に pause point を入れ、次の各操作が完了した直後に SIGKILL できるようにした。

| crash point | kill 直後の table | strict 診断 | 診断前後の DB tree hash |
|---|---|---|---|
| `embedding_identity` 確認後 | identity のみ | `writer_heartbeat` 欠落で失敗 | 一致 |
| `sections` 作成後 | identity + sections | 同上 | 一致 |
| `index_requests` 作成後 | identity + sections + index_requests | 同上 | 一致 |
| `writer_heartbeat` 作成後 | identity + 必須3 table | 合格 | 一致 |
| `index_requests.status` index 作成完了後 | identity + 必須3 table | 合格 | 一致 |

各 pause は native LanceDB create/index 呼出しの**完了後**である。API 内部の途中、他 scalar index の個別作成点、OS crash / 電源断を再現してはいない。README に単独実行コマンドを記録し、`pnpm --dir packages/mcp-server exec ../../node_modules/.bin/vitest run --config vitest.config.maintenance.ts src/maintenance/__tests__/parallel-mcp-startup.test.ts` を実行したところ、1件成功（9.731秒）した。通常 config は実モデル用 global setup を起動するため、このテストには maintenance config を指定する。reviewer も前 HEAD で同テスト1件の成功を独立確認している。dist が現在の source と一致することは harness では証明していないため、結果は `pnpm build` 後の同一 checkout に限って読む。

最終実行は macOS / 単一 host / local temporary filesystem。`lock-control.mjs` の20 race は全て片方のみ成功（この回 shared 13 / exclusive 7）。`recreate-recovery.mjs` は上の5 crash point、source 不在時に不変で拒否される recreate、source 復帰後の全 recreate、index + documents backup restore の hash 一致を確認した。backup restore 後は DB strict 診断に通る一方、既存 `incomplete` は残って shared registration を止める。fake embedding は固定 vector のみで、request は18回。

writer fault は、reviewer 指摘に合わせて signal-0 の存在確認は通し、`SIGTERM` 送信に限って MCP process 内で `EPERM` を注入するよう直した。診断 child group は生存し、MCP は exit 0、`users` は1件保持、exclusive は拒否、`WATCHING` なし、sections 0件だった。終了後 harness が child group の消失と temp root 削除まで確認した。これは元の実環境で EPERM が起きた原因の特定ではなく、SIGTERM send failure を実サービス境界に注入した試験である。

loopback bind が sandbox で `EPERM` となったため DB / service / 5 MCP harness は sandbox 外で実行した。`node --check`、`git diff --check` と cleanup failure self-test は成功。native API 内部 crash、multi-host/shared filesystem、実データ、dist/source 対応、実運用の EPERM 原因は未検証のまま。

### #183 と conductor への報告

#180 は `COMPLETED` として手動 close された履歴だけを確認し、閉じ直した根拠は Issue 履歴から特定できない。#180 の受け入れ条件・state はこの作業では変更していない。再現資材の改善と上記実測を conductor に報告する。shutdown が exit 0 でも子が残る契約、部分 DB の正式な回復先、backup 復元後の `incomplete`、format/readiness と対象 filesystem は引き続き未決定である。これらの製品仕様には operator decision が必要であり、実装には入らない。

**停止未確認時の shutdown 契約**は、次の選択肢を conductor に返す。

| 選択肢 | 帰結 |
|---|---|
| 親プロセスの exit 0 は「親が終了した」のみを示すと定義する | 現行の観測と整合するが、サービス利用者には子が残る終了を成功と誤認させるおそれがある。`users` 保持と運用ログを別途確認する必要がある。 |
| 子の停止を確認できなければ shutdown を失敗として報告し、`users` は保持する | 成功と完了を区別でき、破壊的 maintenance は引き続き拒否される。MCP / HTTP の終了 status と再試行方法を決める必要がある。**推奨**。 |
| SIGTERM 失敗後に追加 signal / force kill を試みる | 一部の停止競合を短縮できる可能性があるが、EPERM の権限不足は解消しない。platform ごとの signal 順序・待機時間・停止確認条件が必要で、単純な fallback として採用しない。 |

この推奨は exit 0 の実測と「停止未確認中は利用登録を解放しない」という既存保護に基づく。operator が shutdown completion の利用者向け意味を決めるまでは、製品の終了動作は変更しない。

## operator decision inq-1 の記録（2026-11-27）

operator は inq-1 で「単一 host を対象とし、複数 host は非対応と明記」を選択した。この選択を以後の設計比較に適用する。上記の host 対応範囲の比較では multi-host 対応案を採用候補から外し、対応範囲は単一 host として説明する。

この決定は、#180 の SIGKILL 条件を狭めるものではない。また stale lock の自動回収、新しい lock 方式、永続状態、format / migration、maintenance recovery の仕様を承認するものでもない。#180 の受け入れ条件はそのまま維持する。

単一 host でも filesystem 上の前提は残る。全協調 process が同じ実体の DB と management directory を使い、競合する directory `mkdir` が原子的に一方だけ成功し、作成・削除の状態が各 process に必要な時点で可視になる必要がある。障害・再起動後の marker の永続性も filesystem と操作に依存する。`strictMaintenanceLock()` が確認する canonical path、標準配置、`st_dev` の一致は、この動作保証の代わりにはならない。ローカル一時 filesystem 以外の同一 host 利用（shared/network filesystem を含む）は指定環境で実証しておらず、対応済みとは扱わない。

記録時点の実装観察では `MaintenanceLock` は `gate` と `exclusive` を directory `mkdir` で取得し、`users` は利用者ごとの directory として登録する。owner host / PID / fencing token は持たない。`incomplete` の作成・完了処理では directory sync を行う箇所があるが、全 marker 操作を一律に sync する実装ではない。このコード観察は単一 host 内の必要前提を整理するものであり、現行 lock の維持・耐久性の承認ではない。

同日の GitHub timeline を再確認したところ、#180 は `05:51:34Z` close、`06:32:55Z` reopen、`07:23:33Z` 再 close（いずれも actor `otolab`）で、現在 `CLOSED / COMPLETED`。close event に commit はなく、再 close の理由は履歴から特定できない。依頼どおり状態と受け入れ条件は変更していない。
