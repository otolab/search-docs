# Issue #167: Embedding PID のポート別管理と所有権確認

## 作業状態

実装・セルフレビュー・対象検証済み。PR 作成前の conductor 報告段階。結果は [Issue コメント](https://github.com/otolab/search-docs/issues/167#issuecomment-7232421240) に記録済み。

## 実装方針

- 管理ファイルは `embedding-<port>.pid` とする。旧 `embedding.pid` は読み取り互換を維持するが、旧形式には起動元識別子がないため、通常 stop の所有権根拠にはしない。明示 `stop --port` は既存の外部サーバ停止契約を維持する。
- 起動ごとにランダムな launch token を作り、Embedding Python プロセスの内部起動引数へ渡す。readiness 後、LISTEN PID のコマンドラインに同じ token があり、取得した PID がポート所有者と一致する場合に限り、新形式 PID ファイルを公開する。
- 通常 stop も PID・port owner・launch token を照合する。不一致・取得不能・旧形式は kill せず、明示ポートを指定して対象を確認するよう案内する。起動失敗時の cleanup は spawn した launcher tree のみを対象にする。
- `/health` と外部 embedding API は変更しない。PID identity の照会と signal の間は OS 標準 PID 操作では原子的にできないため、直前再確認で競合窓を狭め、残る制約を文書に明記する。

## 受け入れ観点

- [x] ポート競合の順序を制御して誤登録と後続 `stop` の挙動を再現し、実 OS で再現できない場合は制約を記録する。
- [x] 対応 OS ごとの所有権確認方法と、確認不能・プロセス終了・PID 再利用・競合時の安全策を定める。
- [x] 無関係なサーバを管理対象にせず、正常起動・停止・再起動を含む回帰を確認する。
- [x] 外部サーバ検出と `embedding stop --port` の契約、既存 PID ファイル、利用者向け説明を確認する。

## 調査結果

### 現状と再現条件

`embedding start` は `packages/cli/src/commands/embedding/start.ts` で、起動前に既存サーバを検査し、ポートが空いていれば `uv` を detached で起動する。その後の readiness はポートへの応答だけで判定する。launcher の終了を確認した後、同ポートの LISTEN PID を取得して PID ファイルへ保存するが、その PID が今回 spawn した launcher の子孫かは確認していない。

誤登録は次の順序で起き得る。

1. 起動前検査では health 応答がなく、ポートも空いている。
2. CLI が launcher を起動した後、別の Embedding サーバが同じポートを bind して readiness に応答する。
3. launcher の終了イベントがまだ処理されていない状態で、CLI がポート所有 PID を取得し、PID ファイルへ保存する。
4. 通常 `embedding stop` が PID ファイルの PID と同じポートの所有 PID の一致を見て、そのプロセスを停止する。

#165 の調査で、この順序を固定したモックでは別サーバ PID が保存されることを確認済み。実 OS での発生頻度・再現は未確認。現行 `start.test.ts` にも `getListeningProcess` が launcher PID と異なる PID を返すと、その PID を保存して `status` / `stop` へ渡すテストがある。一方、外部サーバを起動前検査で検出する通常ケースのテストだけでは、この検査後の競合を覆えない。

### 所有権と失敗時の安全性

`getListeningProcess` が返す LISTEN PID だけでは、今回の起動との関係は分からない。実装では、起動ごとに作る UUID を Python の hidden startup argument に含め、LISTEN PID のコマンドラインに同じ UUID があるかを照合する。readiness の後と PID 公開の直前に PID・marker を照合し、通常 stop の直前にも記録 PID・現在の LISTEN owner・marker を照合する。照会不能・不一致・プロセス終了・PID 再利用では登録や通常 kill を拒否する。

- **macOS/Linux**: LISTEN owner は既存の `lsof` / `ss` / `netstat` 経由で取得し、コマンドラインは切り詰めを避ける `ps -ww` で取得する。startup cleanup は現在の launcher command に marker がある場合のみ detached process group に行う。group がなくなったときは PID 数値へ fallback しない。
- **Windows**: LISTEN owner は既存の `netstat -ano`、process command line は PowerShell/CIM で取得する。照会失敗・権限不足なら marker を確認できず、登録 / 通常 stop / startup cleanup は拒否される。実機未検証。
- **共通の残余リスク**: marker は起動元との対応を確認する目印で、同一ユーザーの悪意あるプロセスに対する認証ではない。PID/owner/marker の最終照合後から OS に signal を渡すまでの入れ替わりは、安定 process handle を保持する OS 共通 API を使っていないため排除できない。

### PID ファイルと既存契約

変更前は `~/.search-docs/embedding.pid` の単一 JSON ファイルで、`pid`, `port`, `startedAt` と任意の `model`, `dimension`, `logPath` を保持していた。`status --repair` と stale 起動時の修復も固定パスを削除していた。

実装後は start / stop / status / repair が対象ポートのファイルを選び、別ポートの記録を消さない。旧 `embedding.pid` は同じ JSON schema の読み取り互換を残すが、marker がないため通常 stop では信用しない。status には unverified legacy record と表示し、stale repair は選択した旧ファイルだけを削除する。

`embedding stop --port <port>` は PID ファイルがない外部サーバも明示ポートで停止できる既存契約を維持した。複数ポートの管理記録がある場合、引数なし `stop` / `status` は曖昧として拒否し、`--port` を要求する。

`docs/cli-reference.md`、`docs/user-guide.md`、`docs/architecture.md` は単一の `embedding.pid` と引数なしの挙動を記載しているため、保存形式と互換性方針に合わせて更新が必要。`EmbeddingServerProcess` にも readiness をポート応答だけで見る別経路があるが、管理 PID を保存して通常 `embedding stop` に引き渡す今回の Issue とは影響が異なる。スコープを広げず、必要なら conductor に分けて報告する。

## 実装・検証結果

- `embedding-<port>.pid` に分割し、旧 `embedding.pid` は読み取り互換を維持。status/stop の引数なし選択は対象が一意な場合のみ許可し、複数ポートは `--port` を要求する。修復・停止は選択したファイルだけを削除する。
- 起動ごとに UUID の launch identity を Python の非公開起動引数へ渡す。readiness 成功に加えて、LISTEN PID のコマンドラインで同じ identity を確認し、PID ファイルの公開直前にも owner が変わっていないことを再確認する。旧ファイルや照合不能な owner は通常 stop で信頼せず、明示 `stop --port` の外部停止契約は維持する。
- 起動失敗時の cleanup は launcher の現在のコマンドラインに同じ identity がある場合に限る。Unix では専用 process group を対象にし、group が消えたとき PID 数値へ fallback しない。公開後に launcher の異常終了を検出しても追加 kill は行わない。
- `packages/cli/src/commands/embedding/__tests__` と `packages/cli/src/utils/__tests__` に、順序制御 unit regression、旧形式・複数ポート・stale record・同一 PID / identity mismatch・owner 交代・外部 stop・cleanup を追加した。最終実行は 7 files / 59 tests passed。
- fake `uv` と HTTP server を使う process test で、macOS 上の次の順を再現した: 空きポート確認 → launcher 起動・生存 → 競合サーバが bind/readiness 応答 → owner identity 不一致 → 登録拒否と launcher tree cleanup。競合サーバの `/health` と LISTEN が残り、旧形式 PID では通常 stop が拒否されることを確認した。
- 同じ process test で正常 start / stop / restart、2ポート同時管理、明示ポートで片方だけ停止することを確認した。macOS 実行時に default port 24281 は別の embedding server が使用中だったため、競合テストは空いているランダムポートを使用した。
- Windows は実機未検証。PowerShell/CIM で process command line を取得し、取得不能なら照合失敗として登録・通常 stop を拒否する。Linux 実機でも未検証で、CI 結果の確認が必要。
- PID照合後から signal までの OS 共通な原子的保証はない。launch identity は偶発的競合・PID再利用との対応確認用であり、同一ユーザーの悪意あるプロセスに対する認証ではない。両方を利用者向け docs に記載する。
- 変更した本体 6 モジュールは一時 module stub を使った strict TypeScript check を通過。Python server と lifecycle regression script の syntax check、`git diff --check` も通過した。
- 通常の全 unit suite と `tsc --build` は、worktree に `node_modules` がないため main worktree の古い package dist / declaration に解決され、外部依存の export/type 不整合や sandbox の loopback `EPERM` で失敗した。失敗箇所は今回変更した実装ロジックではなく、対象 59 tests と対象 module type check は独立に通過した。Linux / Windows の CI・実機結果は未確認。

PR はまだ作成していない。上記結果を conductor へ報告し、次の指示を待つ。

## 複雑性と未確定点

当初見込みどおり複雑性は中〜高だった。変更は start に加え stop / status / stale repair / legacy fallback に及んだ。macOS 上の実プロセス検証と対象 unit test は通過。通常の全 unit suite は、別パッケージの stale dist / node_modules 解決に加え、sandbox 内の loopback `EPERM` で失敗したため、対象 suite は一時的な依存 alias と sandbox 外実行で分けて確認した。最終報告ではこの制約と検証範囲を明示する。

コマンドライン起動識別子の方式は `/health` に変更を加えず OS 共通の PID owner と起動を結び付けられる一方、OS API が提供する安定 process handle を保持しない。Windows / Linux の実機検証は残っている。コマンドライン照会に失敗した場合と marker が見つからない場合は登録・通常 stop を拒否する。
