# Issue #155: Python 終了時クラッシュと heartbeat 統合テスト

## 作業方針

- Issue 本文・コメントを source of truth とし、受け入れ観点を「Python 終了時の native crash の調査」「テスト構造の見直し」「heartbeat の意味を保った対処」「連続実行による検証」として扱う。
- 公開 CI の失敗ログ、workflow と依存固定方法、Python 補助プロセスの起動・終了経路を確認する。再実行成功は原因特定や修正の証拠に数えない。
- まず現行テストが証明している性質を切り分ける。Python 補助プロセスをなくす・長寿命化する場合も、実 LanceDB を使うこと、別タイムゾーンの writer の fresh heartbeat を尊重すること、期限切れ後に takeover することを保つ。
- 原因を再現できた場合は根拠のある回帰検証を追加する。再現できない場合は、根本原因未確定のままテスト構造または終了経路への最小対策を選び、限界を記録する。
- PR 作成前に変更範囲・検証結果・未確定事項を conductor に報告する。マージは行わない。

- 2026-11-26: 1回目の公開 run 44266063191 は `heartbeat-integration` の該当テストのみ失敗。失敗stepのraw logにはPython環境と依存のinstall一覧が残っていた。
- 2026-11-26: 作業ツリーは `ensemble/issue-155`、`origin/main` 直上で開始時点の差分なし。
- 2026-11-26: 2回目の公開 run 45829919932 の試行2でも、同じテストの2回目の `runWriter(121)` で同じ fatal error が起きている。試行3は成功したが、これは原因解決の根拠にはならない。失敗ログは [run 44266063191](https://github.com/otolab/search-docs/actions/runs/44266063191/attempts/1) と [run 45829919932 attempt 2](https://github.com/otolab/search-docs/actions/runs/45829919932/attempts/2) で公開されている。
- 2026-11-26: 両方の失敗は `runWriter(0)` の直後ではなく、独立Python process からの `runWriter(121)` 時（テスト113行目）に発生。既にNode側の `DBEngine` Python worker が同じLanceDBを開いている状態で、短命な `python -c` process が書き込み後に finalization している。終了時のLanceDB / PyArrow等との競合は疑えるが、公開ログだけでは原因を断定できない。
- 2026-11-26: 失敗した2 attemptはいずれも `ubuntu-26.04`、x64 CPython 3.11.18。`uv sync` は43 packageをインストールし、LanceDB 0.30.2 / PyArrow 22.0.0 / NumPy 2.3.5 / Pandas 2.3.3 / pylance 0.39.0などの版がraw logから確認できた。`uv.lock` はないが、各runのログには実際にinstallした43 packageの版が記録されている。11月18日のrunと11月26日のrunでは直接依存の主要版は同じ一方、推移依存8 packageの版が変わっていた。日付をまたぐと依存解決結果が変わることが分かる。
- 2026-11-26: PR #177 の成功した `heartbeat-integration` run（45838058320）は、失敗した run 45829919932 attempt 2 と同じ `ubuntu-26.04` / CPython 3.11.18 x64、およびinstall済み43 packageの版が一致していた。変更後テストが失敗時と同じ記録上の環境で通ったことは確認できる。ただし、元のfatal errorの原因そのものを特定したわけではない。
- 2026-11-26: `table_names()` のDeprecationWarningも記録されるが、fatal errorとの因果関係は未確認。`os._exit()` や条件付き再試行はデータflushを飛ばす／失敗を隠すため、根本原因を説明する根拠なしに採用しない。
- 2026-11-26: Issue #155に調査・判断の署名付きコメントと、PR #177 のCI結果を追記した。PRにも両job成功と元の原因が未確定である旨をコメントした。

## 作業記録

- 短命な `python -c` でtimestampを直接書き換える構造をやめ、LA側のNode child processに通常の `DBEngine` APIでheartbeatを書かせる形に変更した。childをheartbeat失効まで生存させ、東京側のWatcherがfresh時にclaimせず、1秒の期限切れ後にtakeoverすることを実 LanceDB で検証する。
- `skipInitModel` 接続ではwriter heartbeat tableが初期化されないため、既存のDBEngine統合テストと同様にローカルhealth stubを立て、通常初期化で必要なtableとindexを作る。
- `uv python install 3.11.18` はこのホスト向け `cpython-3.11.18-macos-aarch64` の配布がなく失敗。ローカルではPython 3.11.13、macOS ARMで実施した。CIのLinux/Python 3.11.18とは同一条件でない。
- ローカル依存は `uv sync --project packages/db-engine --python 3.11` で準備した。`uv.lock` がないため推移依存は実行日の解決結果であり、失敗時の環境と同一ではない。CI各runのraw logには、そのrunで実際に入った43 packageの版が記録されていた。
- 検証: `pnpm build`、root `pnpm lint`、fixture `node --check`、`git diff --check` が成功。対象heartbeatテスト単体が成功し、macOS ARM / Python 3.11.13で独立Vitest起動を50回連続して全件成功した。ローカルのheartbeat suiteは11件中10件成功で、未変更の診断timeoutテストだけ `Error: kill EPERM` により失敗した。
- PR #177 のLinux CIではheartbeat-integration（2分8秒）とbuild-and-test（5分19秒）が成功。heartbeat runのOS/Python/実install package setは、失敗した11月26日attempt 2とログ上同一。macOSで同じPython patch版を動かせなかった制約は残るが、PR CIで対象Linux環境の確認を行えた。
- 2回の失敗は短命なPython補助processが書き込み後にinterpreter finalizationする時点で発生。終了経路をテスト構造から除き、失敗した2回目のattemptと同じ記録環境で新テストが成功したため、テスト内の再発を避ける対処として妥当と判断した。一方、C extension / LanceDB等のnative finalizationに関する根本原因は未特定で、製品コードの別経路で起きるかも未確認。
