## CI / review follow-up（2026-11-27）

- PR #187 の run `46007050689` は commit `24cf69d` を対象にし、`build-and-test` は成功、`heartbeat-integration` は失敗した。ログ上の失敗は `index-delete-integration.test.ts` の引き継ぎ2件で、片方は別接続からの `processing` 状態が直ちに見える前提、もう片方は takeover 後の request が `pending` に戻る前提を満たせなかった。これは一時的な CI 揺れではなく、ADR-021 の5秒 read consistency に対して古い snapshot を使う読み取り・復旧処理が残っていたことによる。
- 復旧時の一括更新を新しい LanceDB 接続で行い、統合テストでは最新状態を最大10秒待つ修正を commit `23d1279` に含めた。実 LanceDB の対象2件は `2 passed`。サンドボックス内では `listen EPERM: operation not permitted 127.0.0.1` となったが、許可されたサンドボックス外実行では成功した。GitHub Actions run `46009902708` は `build-and-test` と `heartbeat-integration` の両方が成功。
- 並行レビューで `is_lance_not_found()` が `not found` の部分文字列だけを見ており、`column not found` や `index not found` まで stale snapshot と誤判定する懸念が指摘された。隔離環境で再現した実 LanceDB の欠損ファイル例外は `RuntimeError` で、`Object at location ... not found: No such file or directory (os error 2)` を含む。この形式に判定を限定し、column / index / manifest の一般的な not found は再試行対象にしないテストを追加した。
- 判定修正後の Python 関連テストは `12 passed in 8.68s`。引き継ぎ integration 2件はサンドボックス外で `2 passed`（5件 skipped）。サンドボックス内の同コマンドは localhost bind の `EPERM` で停止した。
- `53878d3` の CI では、元の引き継ぎ2件は通った一方、startup reconciliation の既存 integration で `processing` request の最終状態が `skipped` ではなく `completed` になる失敗が出た。実 LanceDB の同じテストをローカルで実行しても再現した。原因は takeover 復旧が fresh connection に書いた直後、worker の古い connection が `pending` を読み直し、reconciliation が skip 済みの request を処理する race と判断した。
- 修正として bulk update の全経路を新規接続にせず、takeover の `processing` 復旧だけ新しい接続を使う明示 option を追加した。復旧後はその接続と `index_requests` table を worker の現行 cache にするため、続く reconciliation と index worker が同じ書き込み状態を読む。

## purge-safety CI の Python finalization crash 調査（2026-11-27）

- PR head `9093670` の run `46015625182` は `ubuntu-26.04` / CPython 3.11.18。失敗 job の再実行でも同じ `purge-safety.test.ts` の subprocess が終了時に `Fatal Python error: PyGILState_Release: thread state ... must be current when releasing`、`Python runtime state: finalizing` で落ちた。LanceDB 0.30.2 / pylance 0.39.0 / PyArrow 22.0.0 を使用している。
- main の `023308bb` にある対象 test、`purge-safety.ts`、`packages/db-engine/pyproject.toml`、`uv.lock` は PR head と同一。main の CI run `45952911903` も `ubuntu-26.04` / CPython 3.11.18 で同じテストを実行し、6件成功（対象ケース 1.511秒）。直前の PR head green run `46014561896` も同じ runner image / Python 版だった。したがって、少なくともテスト・依存定義・記録された runner image の差では説明できず、現象は Linux CI 上の native resource teardown 時の競合が有力。
- 元の subprocess は同期 `lancedb.connect()` / 同期 index API を使用していた。インストール済み LanceDB の同期 `DBConnection` / `LanceTable` には明示的な `close()` がなく、Python 終了時に Rust-backed resource の解放を任せていた。`lancedb.background_loop` は import 時に daemon event-loop thread を起動する。fatal error が interpreter finalization 中であることも踏まえ、テスト側の lifecycle を変更する。
- 回帰修正として subprocess を `connect_async()` と async index API に移し、完了後に `table.close()` / `db.close()` を明示してから `asyncio.run()` を終了するようにした。LanceDB の async wrapper では index 操作は async、close は同期メソッドであることを実環境で確認した。
- 修正後、隔離環境 `/private/tmp/issue173-venv`（macOS arm64 / CPython 3.11.13、LanceDB 0.30.2 / pylance 0.39.0 / PyArrow 22.0.0）で対象 purge-safety 6件と server unit 全200件が成功。修正前も同じ macOS 環境では対象テストが成功していたため、ローカルでは異常を再現できず、これだけで Linux の crash 解消を証明したとは扱わない。次は PR CI で Linux runner 上の結果を確認する。
