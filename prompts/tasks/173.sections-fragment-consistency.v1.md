# Issue #173: LanceDB の古い読み取りバージョンによる Not found

## 作業計画

- PR #186 の ADR-021 を実装前提にする。PR は Open、`ad3f63d` の1 commitで `docs/architecture-decisions.md` のみを変更し、実装は本 Issue に割り当てている。
- ADR-021 の要点は、read-only / read-write を問わずすべての LanceDB 接続に5秒の `read_consistency_interval` を設定すること、読み取りが `Not found` で失敗した場合にテーブルを開き直して一度だけ再試行すること。
- 全接続・テーブルキャッシュ・読み取り経路を調べ、実 LanceDB で別プロセスの cleanup による stale reader を再現する。その後、同じ経路を回帰テストにして修正を確かめる。ADR-020 の cleanup 10分設定は変えない。
- Issue の再発記録と ADR-021 に齟齬は見当たらない。#171 の FileStorage tmp 名衝突は別問題として対象外にする。
- 予期しない問題、方針判断が必要な点、PR 作成前に conductor へ報告する。マージしない。

## 調査記録

- 2026-11-27: Issue #173、PR #186、PR の ADR-021 差分を確認。Issue は再発後に再開され、原因を非 master の `readOnly: false` プロセスが古い manifest を保持し、master の cleanup が参照ファイルを削除する経路としている。
- 現 worktree は PR #186 未取り込み。`worker.py` の初期化は `read_only=True` のときだけ5秒設定し、通常の server / MCP は `readOnly: false` で接続する。ほかに heartbeat 用の新規接続がある。
- 2026-11-27: 作業用 Python に `lancedb` がないことを確認。既存 global uv cache や venv は変更しない方針にし、`/private/tmp/issue173-uv-cache` と `/private/tmp/issue173-venv` を新規作成して通常の依存取得を試した。次のコマンドは PyPI の DNS 解決失敗で停止した。
  - `UV_CACHE_DIR=/private/tmp/issue173-uv-cache uv --no-config pip install --python /private/tmp/issue173-venv/bin/python lancedb==0.30.2 pylance==0.39.0 pyarrow==22.0.0 pandas==2.3.3 numpy==2.3.5 pytest==9.0.1 psutil==7.1.3`
  - `https://pypi.org/simple/pandas/` の取得が3回再試行後に失敗。`dns error: failed to lookup address information: nodename nor servname provided, or not known`。
  - 先の既存 cache 利用 escalation は `missing field outcome` で実行されず、同じ形では再試行していない。
- 2026-11-27: オペレータの許可を受け、同じ独立 cache / venv で `UV_CACHE_DIR=/private/tmp/issue173-uv-cache UV_PROJECT_ENVIRONMENT=/private/tmp/issue173-venv uv --no-config sync --project packages/db-engine` を実行。依存43件を `/private/tmp/issue173-venv` に導入できた。既存の `VIRTUAL_ENV` は不一致のため無視され、global 環境は対象になっていない。
