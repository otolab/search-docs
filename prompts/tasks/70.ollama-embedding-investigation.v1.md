# Issue #70 Ollama Embedding 調査

## 作業方針

Issue 本文とコメントを受け入れ条件の基準とし、内蔵 ONNX を当面運用する方針を維持して、外部 Ollama の利用に必要な差分を調べる。実装方針の決定と着手は調査報告後の conductor 指示を待つ。

## 順序

1. API 互換性、モデル選定と検出、既存インデックスとの整合性、Docker MCP の文書を現状のコードと照合する。
2. Ollama の一次資料と利用可能なモデルを調べ、実機検証の可否を確認する。
3. 調査結果、必要な変更と検証、未解決事項を Issue と conductor に報告する。

## 見込みと不明点

API の形式確認に加え、モデル名の伝播とインデックスの互換性が複数の層にまたがる可能性がある。Ollama 実機とモデルの利用可否、モデル変更時に既存データを安全に扱う方法を確認する。

## 調査結果（2026-11-20）

- Ollama の `/api/embed` は `model`, `input`, `dimensions` を受け取り、`embeddings` を返す。RemoteEmbeddingModel が使う主要形式は一致するが、実機での動作は未検証。
- 外部サーバは `/health` と `/ready`（または `/health` への fallback）が必要なため、Ollama は選ばれず別サーバへ fallback する。`entrypoint.sh` ではなく TypeScript の EmbeddingServerProcess が検出を担う。
- 仮に検出を通しても、Python worker の `/health` 失敗時はモデル名 `unknown`、次元 `None` のまま。設定値が worker に渡っておらず、コメントにある fallback は成立しない。
- sections のベクトルは固定長スキーマ。既存テーブルは再利用され、次元やモデルの一致確認は見当たらない。次元が同じでも別モデルのベクトルを混在させれば意味空間が異なる。
- 候補は多言語の embeddinggemma や qwen3-embedding:0.6b。日本語検索品質、必要な入力形式、指定次元への対応は未検証。ruri-v3 の Ollama v0.21.0 における失敗は Issue のオペレータ報告を尊重する。
- ローカルに Ollama 0.40.16 クライアントはあるが、11434 のサーバは停止中。実機・Docker MCP の縦断検証は行っていない。
- docs/docker-deployment.md の固定設定や readiness の説明は現状の MCP 経路と照合が必要。MCP の createService は model と dimension を DBEngine に渡していない。

## 実装着手前に判明した接続状態の競合

`DBEngine.waitForReady()` は Python worker の ping 成功時に `isReady = true` とするが、モデル初期化はその後に行われる。並行した `connect()` がこの間に入ると、`worker && isReady` 分岐はモデル初期化を待たず `connectionState = 'ready'` として返る。MCP は `service.start()` と `watcherProcess.start()` から同じ DBEngine に連続して接続を開始する。接続タイミング次第で初期化前を ready と見せ、モデル・インデックスの照合結果が確定する前に利用可能と判定される懸念がある。実行による再現は未実施。

今回の fail closed には接続状態の競合も扱う必要があり、既存利用全般に影響するため conductor に報告して指示を待つ。コード変更なし。

## 実装中に判明した既定 URL の互換性問題

`DEFAULT_CONFIG.indexing.embeddingUrl` は `http://127.0.0.1:24281` で、ConfigLoader は未指定時にも補完する。現行の作業中コードで明示 URL に fail closed を適用すると、既定の通常起動も内蔵サーバを起動できなくなる。既定を未指定にし自動検出へ委ねることが候補だが、既存ファイルに URL を明記した利用者は従来の fallback と挙動が変わるため、移行案と検証が必要。重大な互換性の問題として報告し、作業を停止した。変更は未完成・未コミット。

並行接続の回帰テストは修正前に失敗、修正後に成功。模擬 Ollama と実 LanceDB による識別・検索等のテストも通過。実 Ollama / Docker MCP、文書化、既定設定と移行の検証は未実施。

## 設定 URL の由来調査

現行 CLI `config init` は embeddingUrl を出力せず、MCP init も同関数を呼ぶ。未指定時は ConfigLoader が既定 URL を補完するため、この場合は既定値を未指定にできる。一方、ファイルに書かれた URL の生成元・意図を示す情報はなく、自動生成か利用者指定か判別できない。localhost として判定することも不適切。既存設定の fallback 維持と従来フィールドだけによる厳格接続は、追加の意思表示なしには両立しない。Issue に選択肢を記録し conductor の判断を待つ。暫定コードは未完成。

## 実装・検証結果

conductor の判断に従い、設定ファイルの `indexing.embeddingUrl` は fallback を維持し、`EMBEDDING_URL` は失敗時に停止する。既定 URL は未指定とし、従来どおりローカル共有サーバを先に検出する。モデル・次元・Ollama digest をインデックスに保存して照合し、旧ONNX索引は従来モデルで継続、識別不能な旧索引からOllamaへの切替は停止する。digest は推論前後にも確認する。並行 connect はモデル初期化の成否を共有し、初期化前のDB要求も拒否する。

`pnpm run build:fast` 成功。設定生成・接続・検出・MCP設定のVitest 25件、模擬Ollamaと実Python/LanceDBによる結合テスト1件、Pythonテスト13件が成功。Ollama 0.40.16を一時ポート・空モデル領域で起動し、`/api/tags` が200、`/health` が404であることを確認した。モデルを使った実推論と日本語品質は未検証。Dockerデーモンは停止しておりDocker MCPの実検証は未実施。パッケージのlintスクリプトは環境のPATHでeslintが見つからず実行できなかったが、ルートのeslintを変更済み対象に直接実行しエラーはなかった（対象外として無視されたファイルあり）。PRは未作成。
