# Issue #180: admission 撤廃と並列起動改善

## 現在のゴール

オペレータの指示に従い、まず「複数起動後に admission が残り、その後の通常起動ができなくなる」デグレードを解消する先行修正を行う。Issue の受け入れ条件は維持し、各条件の実証範囲と残課題を分けて報告する。

- 同一プロジェクトで MCP サーバを5本以上同時に起動し、30秒以内にすべて接続する。
- 起動中のプロセスを SIGKILL した後も、後続起動が成功する。
- ロックの種類、取得モード、保護対象を文書化する。

## 作業範囲・制約

- MCP / HTTP の通常起動、Watcher の writer 昇格時再診断、MCP / CLI の通常 repair から admission を完全撤廃する。
- `gate` / `users` / `exclusive` / `incomplete` による既存の共有登録と保守排他、strict 診断の fail-closed を維持する。
- 初期化状態を示す永続情報、新しいロック、PID 等に基づく自動回収は追加しない。先行修正に不可欠と判明したら実装を止めて conductor に報告する。
- 既知の必須テーブル未作成だけ短時間・回数限定で strict 診断全体を再試行する。再試行後も欠落すれば拒否する。破損、一般的な読取エラー、パス安全性違反、identity 不一致、停止未確認は再試行で握りつぶさない。
- 実装・関連テスト・文書・セルフレビューを行い、PR 作成前に conductor へ報告する。この報告後、オペレータの指示により PR #182 を作成した。

## 調査で確かめたこと

- 導入 commit `61b244d` の admission は、strict 診断、DB 初期化、通常 repair を直列化していた。実際の並行 `init_tables()` では、今回のローカル条件で5プロセスすべて成功した。
- 一方、初期化側が `embedding_identity` を作成した後、必須テーブル作成前に strict 診断が heartbeat を読むと、実 DB で `Table 'writer_heartbeat' was not found` が発生した。これはデータ変更ではなく起動失敗だが、MVCC では未作成テーブルを読めない。
- 現行 DB 形式では、初期化中、初期化中の SIGKILL 後、既存 DB の欠落を区別できない。有限の再試行は、生存する初期化との競合だけを吸収し、初期化プロセスが終了した場合は fail-closed のまま拒否する。
- `users` の有効な同一 identity 登録が残る場合、通常起動は追加登録できるが、exclusive 保守は止まる。`gate` または identity のない途中登録が残る場合、通常起動も拒否され得る。owner 情報なしに安全な自動回収を行う根拠はない。
- SIGKILL 後の再起動成功を DB 初期化の任意の時点まで保証するには、今回未承認の初期化状態設計が必要となる可能性がある。通常起動中の `users/gate` 作成窓も別の残課題として扱う。

## 実装順

1. admission API と通常起動・writer 昇格・repair の全利用箇所を削除する。停止未確認時に共有登録を保持する処理は維持する。
2. strict 診断に、必須テーブルの厳密な未作成応答のみを対象とする有限再試行を実装する。
3. admission 撤廃後の lock の振る舞い、再試行後も欠落・破損を拒否すること、Watcher 昇格中 shutdown、通常 repair をテストする。
4. 可能な範囲で実 MCP 5並列・30秒、起動中 SIGKILL 後の再起動、保守 exclusive を縦に検証する。初期化中 SIGKILL の結果とは区別する。
5. `docs/state-model.md` と利用者向けロック説明を更新し、セルフレビュー後に検証済み・未検証・残課題を conductor に報告する。

## PR #182 レビュー対応: macOS worker 停止時の `kill EPERM`

- reviewer は、macOS の実 DB サービス統合試験で CLI `maintenance force-repair` の Python worker 停止時に `kill EPERM` が起き、単独再実行でも再発したと報告した。共有された指摘には詳細 stack trace、失敗した kill の PID / signal、実行権限の情報は含まれていない。
- 作業環境（macOS 27.2.1 / Node v24.16.0）で `strict-service-integration.test.ts` を `require_escalated` で再実行し、148.3秒で成功した。先行の `strict-service-integration` + `strict-multiprocess` 実行でも両試験が成功している。どちらも test 用 Embedding HTTP endpoint と実 DB を用いた。
- detached process group の停止を扱う `process-tree.test.ts` は2件成功。ビルド済み `stopProcessTree` を使った子プロセス停止も5回成功した。今回の再実行では `kill EPERM` を再現できなかった。
- 実装上、`DBEngine.disconnect()` は `stopProcessTree()` の失敗を伝播する。force-repair はその場合に `exclusive` を解放しない。破壊的変更後なら `incomplete` も保持するため、影響は保守と通常利用を止める fail-closed 停止で、ロックを解放して不確かな DB を通常利用へ戻す動作ではない。失敗地点によって `incomplete` がすでに作成済みかは異なる。
- PR diff は `process-tree.ts`、`DBEngine.disconnect()` を含む `db-engine/src/typescript/index.ts`、`maintenance/force-repair.ts` を変更していない。停止処理そのものは既存コードで、統合試験の変更もサービス起動・repair の admission 待ちを削除した箇所であり、force-repair の停止実装には触れていない。一方、この PR の strict 診断再試行が worker の起動回数やタイミングを変えるため、間接的なタイミング影響までは否定できない。
- `EPERM` が OS の process-group signal 拒否なのか、実行 harness / sandbox の制約なのか、あるいは稀な process-group race なのかは、reviewer の失敗環境と詳細ログを得られず確定できない。別環境で成功したことだけでは報告された失敗を否定できず、再現性も未確定。未確認の group kill を直接 child kill に置き換えると子孫 worker を残すおそれがあるため、この証拠だけで停止方式を緩める修正は加えない。

## 残る検証上の注意

- 新規 DB 初期化中に SIGKILL し、DB が部分初期化のまま残るケースは実プロセスで未検証。本修正は有限再試行後も必須テーブルが欠けていれば fail-closed で拒否し、自動修復はしない。
- `gate` 作成途中、または identity のない `users` 登録が残る SIGKILL 窓は今回解消していない。所有者の生存・PID 再利用を安全に判定できる情報がないため、自動回収しない。
- 5本の MCP 起動、DB 初期化前 SIGKILL 後の再起動、実 DB を使うサービスと repair / writer takeover は検証済み。初期化途中 SIGKILL と、writer 昇格診断中 shutdown の実プロセス検証は未達。
