# Issue #144: Embedding provider

## 作業計画

1. 現行の起動・設定・CLI・Python worker の経路と既存の互換性を調査する。
2. provider ごとの責務と設定を整理し、既存設定の振る舞いを維持しながら OpenAI 互換を追加する。
3. HTTP 応答、次元、秘密情報、起動と index / search を検証する。
4. CLI と利用者向け・開発者向け文書を更新し、結果を Issue に記録する。

## 調査メモ

従来の設定ファイル `embeddingUrl` は接続失敗時に自動検出へ fallback する一方、環境変数 `EMBEDDING_URL` は厳格な接続指定である。明示的な外部 provider と区別して維持する必要がある。

## 中断時点

設定・provider の起動・Python 通信に着手したが、依存関係がなく検証できていない。`pnpm install --frozen-lockfile --offline` は必要なパッケージが store にないため失敗。CLI、文書、テストおよび拡張構造の仕上げは未完了。途中の変更は完成品として扱わない。

## 実装・検証（PR 作成前）

Node 依存は `pnpm install --frozen-lockfile`、Python は db-engine の `pyproject.toml` を使った仮想環境で導入した。lockfile は変更していない。設定から HTTP mock、Python worker、索引追加・検索までの経路と、モデル変更による identity 不一致を確認した。既存 Ollama の統合テスト、provider の応答検証、CLI と既存 fallback の対象テスト、ビルド・lint・シェル構文チェックを実行した。

懸念: OpenAI 互換の索引 identity は provider・モデル・次元を記録するが、接続先 URL は含めていない。同じモデル名で別のベクトル空間を返す別ホストに切り替えた場合は自動検出できない。実際の外部サービスへの接続は未検証。

## レビュー対応計画

- OpenAI 互換の接続先を正規化して SHA-256 のみを identity に保存し、旧形式で接続先を確認できない OpenAI 索引は再構築を求める。既存 builtin / Ollama の identity は変更しない。
- 環境設定と認証の解決を汎用的な設定伝搬と provider adapter の責務に分離し、疑似 provider で追加時の拡張性を検証する。
- CI の unit suite に Python 統合テストが混入し `uv` 不在で失敗したため、Python 環境がある統合ジョブへ移す。

## レビュー対応結果

OpenAI 互換の接続先 fingerprint を既存 identity の digest に保存し、旧 OpenAI identity と異なる接続先を拒否する。既存 builtin / Ollama は従来値を使用する。provider 固有の環境 options・認証準備を adapter に移し、疑似 provider と Python dispatch で拡張を検証した。CI の unit suite から Python 統合テストを分離し、uv のある統合ジョブに移した。ビルド、全 unit suite、lint、HTTP mock 統合テスト、Ollama 統合テスト、Python 対象テストを実行した。

## 再レビュー対応計画

OpenAI 互換 provider の readiness と Python worker は HTTP redirect を追跡せず、3xx をエラーとして扱う。別 origin および HTTPS から HTTP への遷移を含め、転送先へ認証情報を送らないことを回帰テストで確認する。PR 本文の古い identity 制約も更新する。

## 再レビュー対応結果

readiness は fetch の redirect を手動扱いとし、Python の OpenAI adapter は redirect handler で全ての転送を拒否する。301 / 302 / 303 / 307 / 308 について別 origin の 2 サーバで認証ヘッダーが転送されないこと、HTTPS → HTTP の拒否、readiness 成功後に worker だけが redirect を受ける場合を確認した。PR 本文の identity 制約を現行実装に合わせた。
